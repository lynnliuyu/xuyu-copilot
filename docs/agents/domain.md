# Domain Docs

工程类技能在探索本仓库时，应如何消费这里的领域文档。

## 探索之前先读这些

- 根目录的 **`GLOSSARY.md`**
- **`docs/adr/`**：读与即将改动的区域相关的 ADR

这两个文件目前都已存在。若将来某一份不存在，**静默继续**——不要提示缺失，也不要建议提前创建。`/domain-modeling` 会在术语或决策真正被确定时按需补上。

## 文件结构

本仓库是 single-context：

```
/
├── GLOSSARY.md
├── docs/
│   ├── adr/
│   │   ├── 0001-virtual-goods-over-erp.md
│   │   └── ...
│   └── agents/
└── packages/
```

虽然 `package.json` 声明了 `workspaces: ['packages/*']`，但 `packages/` 下的 5 个包是同一条业务流水线的不同分层（网盘读写 → MCP → 闲管家适配 → 公网网关 → 管理端），不是彼此独立的限界上下文：货源、卡密、草稿这些术语跨越多个包。因此使用单份 `GLOSSARY.md`，在文件内按簇分组。

若将来某个包长出了自己独立的语言体系，再引入 `GLOSSARY-MAP.md` 拆成多上下文。

## 使用术语表里的词汇

当你的产出需要指称一个领域概念（issue 标题、重构提案、假设、测试名）时，使用 `GLOSSARY.md` 里定义的词，不要漂移回它明确标注 `_Avoid_` 的同义词。

如果需要的概念还不在术语表里，那是个信号：要么你在发明项目根本不用的词（回头再想），要么这里确实有个缺口（记下来交给 `/domain-modeling`）。

## 与既有 ADR 冲突时

如果你的方案与某条 ADR 矛盾，**显式说出来**，不要悄悄覆盖：

> _与 ADR-0004（服务端发布节流）冲突，但因为……值得重新讨论。_

## 额外的项目文档

`.workbuddy/memory/` 下的内容不属于领域文档，但同样重要：`MEMORY.md` 是运维铁律速查，`REFERENCE.md` 是详细参数与清单。它们的入口写在根目录 `AGENTS.md` 的上下文指针表里。
