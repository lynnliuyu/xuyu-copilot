# 开源软件公众号 · 合规与下架流程（定稿）

> 2026-10-09 · 适用范围：本公众号「开源软件分享」全部内容（文章 + 网盘转存包 + 关键词自动回复）
> 上游文件：`docs/开源软件公众号-运营方案.md`（§5.3 随包说明模板 · §6.2 授权声明区块）
> 相邻文件：`docs/开源软件公众号-首批选题与授权核验报告.md`（授权分级）、`docs/开源软件公众号-freeware条款核查.md`（freeware 口径）
> 一句话立场：**我们只做「原样转存 + 中文使用说明」，不做修改版、不做破解版。出现争议时，先下架、再核实、不争辩。**

---

## 一、文档要解决的问题

开源软件分享最怕三件事，本文档逐一给死规则：

| 风险 | 后果 | 对应章节 |
|---|---|---|
| 授权陈述写错（把 freeware 写成开源、把「可分发」写成「可商用」） | 虚假授权陈述 → 侵权投诉、平台处罚 | §2 免责声明 · §3 授权区块规范 |
| 收到权利人通知后**拖、辩、装没看见** | 从民事纠纷升级为恶意侵权，平台直接封号 | §4 下架响应流程 |
| 出了事**拿不出证据**（当时的协议原文、核验记录都没存） | 无法自证「已尽合理注意义务」 | §5 留档要求 |

## 二、文章末尾免责声明（定稿 · 直接复制）

### 2.1 主版本（公众号文章末尾 · 通用）

```
────────────────────────
【免责声明】

本文所介绍软件均为其原作者发布的**开源或官方免费版本**，著作权归原作者所有。
本公众号不制作、不发布任何修改版、破解版或去授权版；所提供的安装包为
**上游官方发布的原文件，未做任何修改**，仅作转存与中文使用说明。

软件按「原样」提供，不附带任何形式的担保。因使用本软件造成的任何直接或
间接损失，本公众号不承担责任；请在安装前自行确认软件是否满足你的使用需求。

授权信息以软件官方仓库/官方页面的条款为准。若你计划**商业使用**，请先自行
前往官方页面确认授权范围（部分免费软件商用需另行购买授权）。

如权利人认为本文或所提供的下载内容存在不当，请通过
<公众号后台留言 / 联系邮箱：____@____>  与我们联系，并提供权利证明。
我们承诺：**收到通知后 24 小时内先行下架，再行核实**，绝不拖延。
────────────────────────
```

### 2.2 变体 A —— 开源项目（GPL / MIT / Apache / BSD 等）

在 §2.1 基础上，把第一段替换为**授权区块**（见 §3.1），并在末尾追加一句：

```
本软件依据 <协议名> 协议分发，我们已随包提供该协议的完整文本，并保留原作者的
版权声明。GPL/A(GPL) 系软件已随包提供源代码获取方式（见包内《SOURCE-获取方式.txt》）。
```

### 2.3 变体 B —— 官方免费软件（freeware）

⚠️ **必须替换措辞，不得套用开源版本**（详见 `freeware条款核查.md` §7）：

```
本文所介绍软件为**官方发布的免费版本（freeware），并非开源软件**。
官方条款允许在**非商业渠道**以**原样安装包**形式分发；本公众号据此转存，
未做任何修改，也未用于销售。

⚠️ 该软件的使用范围受官方条款限制（例如：企业/商业用途需另行购买授权；
不得用于军事相关领域；不得销售）。请在安装前阅读官方条款原文。
```

### 2.4 变体 C —— 只介绍、不代存（如 RunJS、Mp3tag macOS 版）

```
本文**仅作软件介绍**，不提供安装包转存。请前往官方网站自行下载，并遵守其条款。
```

> ⚠️ **变体 C 的文章不得配置关键词自动回复链接。** 只给官网地址 —— 一旦给了网盘链接，「只介绍」就成了空话。

### 2.5 随包《本包说明.txt》末尾固定句

```
如权利人认为本分发不当，请联系 <联系方式>，我们将在收到通知后立即下架并
停止一切形式的再分发。
```

## 三、授权区块规范（文章正文 ⑤ 区块）

### 3.1 开源项目（沿用运营方案 §6.2，此处为最终口径）

```
【关于授权】
本项目 <项目名> 采用 <协议名>，原始仓库：<仓库地址>。
本公众号所做的整理工作为：中文说明编写、安装流程梳理、官方安装包转存。
软件著作权归原作者所有。本文不提供任何修改版、破解版或去授权版。
如需商用，请自行前往原始仓库确认协议条款。
如权利人认为本文或所提供下载存在问题，请通过 <联系方式> 告知，我们将第一时间处理。
```

### 3.2 三档措辞对照（**写错即违规**）

| 授权类型 | 可以说 | **绝不能说** |
|---|---|---|
| MIT / BSD / Apache / ISC | 「开源协议，允许再分发与商用」 | — |
| GPL / LGPL / AGPL | 「开源协议，允许再分发；须保留版权声明与许可证全文」；AGPL 另注明「网络服务场景有额外义务」 | 「随便用」「无任何限制」 |
| freeware（XnViewMP / Mp3tag） | 「官方免费版本，允许非商业渠道原样分发」 | ❌「开源」 ❌「免费可商用」 ❌「无限制」 |
| source-available（BSL/SSPL/Elastic 等 D 类） | —— | ❌ 一律不收录、不介绍、不转存 |
| 无许可证 / 商业软件 | —— | ❌ 一律不收录、不转存；只可「变体 C」介绍 |

### 3.3 平台敏感词（自检清单）

正文、标题、封面、**网盘分享页文件名**四处都要过一遍：

- ❌ `破解` `激活` `crack` `keygen` `去授权` `绿色版（若含破解含义）`
- ❌ `免费`（改用 `开源` / `官方免费版` / `直接下载`）· `永久` · `全网最低` · `可商用`（freeware 场景）
- ❌ `最强` `第一` `最好用`（绝对化用语）
- ⚠️ 标题：闲鱼规则「30 字上限，数字与特殊字符各占 2 位」不适用于公众号，但**公众号标题建议 ≤ 22 字**以保手机端不折行。

### 3.4 ⭐ 分发类 / 介绍类：两类条目，两套动作（**发布前必须判定**）

同一个「写文章」的动作，在两类条目上法律含义完全不同 —— 介绍不侵权，代存代发才是分发行为。

| | **分发类**（可代存） | **介绍类**（不代存） |
|---|---|---|
| 判据 | 授权明确允许再分发（A/B 类开源；freeware 条款写明允许） | 授权不允许再分发，或**存疑未证实**（无许可证 / 商业软件 / Live2D 类专有核心 / freeware 未授予） |
| 文章 | 正常写，套对应授权变体 | 正常写（**介绍本身不侵权**），但授权区块用「变体 C」 |
| 关键词自动回复 | ✅ 给网盘链接 | ❌ **不给链接**，只给**官网 / 官方仓库地址** |
| 网盘 | 建目录、传包 | ❌ 不建目录、不传包 |
| 当前名单 | 见 `manifest.json` 中 `redistributable` 非 `no` 的条目 | `mp3tag`（macOS 版）、`runjs`、`bongocat`（Live2D 专有核心）等 |
| 台账字段 | `manifest.json` 的 `redistributable: yes` / `conditional` | `redistributable: no` |

⭐ **拿不准时一律按介绍类处理** —— 给官网地址的损失只是「读者多点一下」，而错发一次的代价是下架 + 信任损失。
⭐ **存疑 ≠ 可以发**：像 `bongocat` 那样「不确定内置组件能否再分发」的，就是介绍类（判据细节见 `docs/开源软件公众号-F级资源核查.md`）。
⭐ 关键词表（`docs/开源软件公众号-关键词自动回复配置表.md`）已按该字段分档；**新增条目时先判定这一栏，再决定要不要配链接**。

## 四、下架响应流程（SOP）

> **总原则：先下架、后核实、不争辩、全程留痕。**
> 权利人只要给出**看起来合理的权利主张**，就先下架 —— 下架的代价是零，拖延的代价是封号。

### 4.1 接收渠道

| 渠道 | 处置 |
|---|---|
| 公众号后台留言 / 私信 | 每日固定巡检（建议早晚各一次） |
| 联系邮箱（须在每篇文章与随包说明里公开） | 同上 |
| 平台转达（微信/公众号官方通知、网盘平台通知） | **最高优先级**，视为已确认通知 |
| 第三方转告（读者、同行） | 按普通线索处理，但仍需回复 |

**留痕起点**：收到的那一刻就要截图/存档，记录**时间 + 渠道 + 原文**。

### 4.2 分级响应（按通知内容）

| 级别 | 情形 | 动作 | 时限 |
|---|---|---|---|
| **L1 · 明显侵权** | 权利人明确指出某包/某文侵权，或平台下发通知 | **立即下架**（全渠道）+ 停止关键词回复 | **≤ 2 小时**（收到即办） |
| **L2 · 权利主张但事实待核** | 有权利证明，但对「是否真的侵权」需核实 | **先下架**，再核实，核实结果告知对方 | 下架 ≤ 24 小时 |
| **L3 · 存疑／无权利证明** | 仅口头主张、无权利证明 | 先下架（宁松勿紧），同时礼貌索要权利证明 | 下架 ≤ 24 小时 |
| **L4 · 恶意/竞品投诉** | 明显无依据、反复骚扰 | 仍先下架（避免平台介入），保留证据，按 §4.5 处理 | 下架 ≤ 24 小时 |

> ⚠️ **不存在「先核实再下架」的档位。** 所有级别第一步都是下架 —— 因为「下架」不产生任何不可逆损失，而「核实期间继续挂着」正是把民事纠纷变成平台处罚的那一步。

### 4.3 标准处理步骤（逐条执行，不可跳步）

```
① 记录（T+0）
   · 截图/导出通知原文，记录：时间、渠道、对方身份、指认对象（哪篇文章 / 哪个包）、
     主张的权利（著作权 / 商标 / 其他）、是否附权利证明
   · 建立处置工单：out/compliance/<YYYY-MM-DD>-<序号>-<对象>/ ，把原文存进去

② 立即下架（T+0 ~ T+2h）
   · 公众号侧：删除/隐藏对应文章，或撤下文中下载入口
   · 网盘侧：删除对应分享链接 / 转存包（仅删除被指认对象，不波及无关内容）
   · 关键词自动回复：删除或改指向，避免读者仍能获取
   · 逐项打勾并记录下架时间（这是自证已处置的关键证据）

③ 回复对方（T+24h 内）
   · 告知：已下架、下架时间、已停止分发
   · 若需核实：说明核实进度与预计回复时间（不超过 72 小时）
   · 索要（若尚未提供）：权利证明 —— 措辞须礼貌，不得质疑对方动机

④ 核实（T+72h 内出结论）
   · 复核清单：实际授权（读上游 LICENSE / 官方条款原文）→ 我们的分发行为是否越界
     （是否改动过？是否商用？是否超出授权范围？）
   · 结论三选一：确实越界 / 未越界 / 无法判定
     · 确实越界 → 维持下架，排查同类条目（见 ⑤），书面致歉并告知后续措施
     · 未越界 → 不自动恢复；须先取得对方无异议，或确认授权依据充分后再上线
     · 无法判定 → **维持下架**（疑罪从有，成本最低）

⑤ 同类排查（T+72h 内）
   · 用同一判据（协议 / 条款 / 分发行为）扫一遍候选池，找出可能同类越界的条目
   · 结果记入工单，并在 manifest / 台账上标注，避免下次再上
   · 常见同类风险：同一作者的其它项目、同一授权模式（如又是 freeware 却当开源写）

⑥ 归档（T+7d 内）
   · 把 ①~⑤ 全过程落到留档目录（见 §5），标注「已闭环」
   · 若是流程缺陷导致（不是个案失误），回到本文档修订规则，并在进度日志里记一笔
```

### 4.4 回复模板

**首次回复（L1~L4 通用）**

```
您好，感谢告知。

我们已收到您的通知，并已立即下架相关内容（文章/转存包/自动回复），
下架时间：<YYYY-MM-DD HH:MM>。

我们的定位是转存上游官方发布的原始文件并附带中文使用说明，不做任何修改版或
破解版。若本次仍存在疏漏，我们深表歉意。

如方便，可否提供权利证明（著作权登记/商标/官方页面截图等）？我们将在核实后
<3 个工作日> 内回复处理结果，并在确认无误前保持下架状态。
```

**核实后 · 确实越界**

```
经核实，我们的分发确实超出了该软件的授权范围。已做如下处置：
1) 相关文章与下载入口已于 <时间> 全部下架，且不再恢复；
2) 已排查同类内容，<N> 条做同样处理；
3) 已修订内部审核流程，避免再次发生。
由此给您带来的困扰，我们再次致歉。
```

**核实后 · 未越界（措辞要点）**

```
经核实，该软件依据 <协议名> 授权，允许在不修改的前提下再分发（依据：<链接/条款原文>），
我们分发的亦为官方原版未修改文件。

不过我们仍尊重您的意见，目前已保持下架状态。若您确认可以恢复，我们将重新上线；
若您希望维持下架，我们也会照办，不再恢复。
```

> ★ 关键：**即使自认无错，也不主动恢复上线**。把「恢复」的决定权交给对方 —— 这场博弈里我们要的是「不出事」，不是「争对错」。

### 4.5 恶意/滥用投诉的边界

- 同样**先下架**（避免平台介入），但：
  - 不承诺赔偿、不承认侵权（措辞用「已下架，未对事实作出认定」）；
  - 完整保留证据，必要时依平台规则申诉；
  - 若同一主体重复无依据投诉，改由统一渠道书面往来，不再逐条即时响应（但仍下架）。
- **绝不**：与对方公开争吵、在文章里指名道姓反驳、发动粉丝反击。

## 五、留档要求

> 目的：出了争议时能**自证已尽合理注意义务**，而不是空口说「我们核验过」。

### 5.1 两类档案

| 类型 | 内容 | 位置 | 保留期 |
|---|---|---|---|
| **常规核验档**（每个条目一份） | 授权取证记录 | `out/`（现有产物）+ `out/source-notes/<id>/` | 长期（条目下架后仍保留） |
| **争议处置档**（每次投诉一个工单） | 通知原文 + 下架证据 + 核实过程 + 回复往来 + 结论 | `out/compliance/<YYYY-MM-DD>-<序号>-<对象>/` | **≥ 3 年**（诉讼时效参考） |

### 5.2 常规核验档：每个条目必须能回答这 8 个问题

| # | 字段 | 来源 |
|---|---|---|
| 1 | 项目 id / 名称 / 官方仓库或官方页 | `manifest.json` |
| 2 | **协议名（SPDX）** 与**取证文件真实文件名** | `out/gh-audit.json`（`licenseFile`，读仓库文件树得到的真实名） |
| 3 | **许可证正文**（原文留档，非仅结论） | ✅ `out/source-notes/<id>/LICENSE-原文.txt`（由 `make-source-note.mjs` 从缓存逐字抄录，多许可证文件全部收录） |
| 4 | 是否有第三方资源（`vendor` / `fonts` / `models` 等强信号） | `gh-audit` `thirdPartyFiles` + **人工核查结论**见 `docs/开源软件公众号-F级资源核查.md` |
| 5 | 分发义务（GPL 附源码获取方式 / Apache 带 NOTICE / …） | `gh-audit` `obligation` + `make-source-note.mjs` 的「内置第三方组件」段 |
| 6 | 对应版本 tag + 安装文件名 + **sha256** | `gh-audit` `latestTag` + `out/free-software.json` |
| 7 | 核验日期 + 核验工具 | `out/source-notes/INDEX.md` |
| 8 | 随包合规文本是否已生成 | `out/source-notes/<id>/`（`SOURCE-获取方式.txt` + `本包说明.txt` + `LICENSE-原文.txt`） |

> ✅ 现状：1–8 已由 `scripts/gh-audit.mjs` + `scripts/make-source-note.mjs` 覆盖，产物落在 `out/gh-audit.json` / `out/free-software.json` / `out/source-notes/`。
> ✅ **原缺口已闭环（2026-10-09 第 2 轮）**：第 3 项「许可证正文原文留档」过去只在 `.cache/gh-audit/`（7 天过期）里 —— 现已由 `make-source-note.mjs` 固化为随包文件 `LICENSE-原文.txt`（30 条 GPL/AGPL 条目全部落盘，多许可证文件如 calibre 的 `LICENSE`+`LICENSE.rtf`、handbrake 的 `COPYING`+`LICENSE` 均全部收录）。
> ✅ **打包前闸门已脚本化**：`node scripts/make-source-note.mjs --check` 输出 `out/source-notes/CHECK.md`，逐条核 SOURCE / 本包说明 / 许可证正文 / 校验值是否齐备，**有阻塞项时退出码 1**（可直接串进打包脚本做硬闸门）。

### 5.3 争议处置档：工单目录结构（模板）

```
out/compliance/2026-10-09-01-<对象>/
├── 00-通知原文.md          # 时间、渠道、对方身份、指认对象、主张、是否附证明（含截图）
├── 01-下架证据.md          # 逐渠道下架清单 + 时间戳 + 截图路径
├── 02-核实记录.md          # 复核的协议/条款原文摘录 + 我们分发行为的核对结论
├── 03-往来记录.md          # 每次回复的时间、渠道、全文
├── 04-同类排查.md          # 扫描范围、判据、命中条目、处置
└── 05-结论.md              # 闭环结论 + 是否需修订流程
```

### 5.4 留档的四条纪律

1. **见证而非结论** —— 存**原文截图/原文文本**，不只存自己的判定结论。
2. **时间戳为准** —— 每个动作（收到、下架、回复、核实完成）都要有可核的时间。
3. **不可事后美化** —— 下架就是下架，不要回头把记录改写成「本来就没发过」。
4. **不删除** —— 争议档保留 ≥ 3 年；条目下架后，其核验档**仍保留**（正是最需要的时候）。
5. ⭐ **混合资源型项目要分开留档** —— 仓库根许可证只覆盖「作者自己的代码」。`vendor/`（第三方库）、`resources/`（字体/模型/图标）各有各的授权，且**仓库里常常不附这些组件的 LICENSE 文件**（只留一个 `UPSTREAM` 版本记录）。
   → 判定与留档必须**回到各组件上游仓库**取许可证正文；结论落 `docs/开源软件公众号-F级资源核查.md`，随包要求由 `make-source-note.mjs` 的「内置第三方组件」段自动写出。

## 六、发布前合规闸门（Checklist，逐项打勾才发）

```
□ 授权已核实：读的是**上游许可证正文/官方条款原文**，不是清单登记
□ 授权分级不是 D / E（source-available / 无许可证）
□ 免责声明已套用正确变体（开源 / freeware / 只介绍）
□ 授权区块措辞与协议匹配（§3.2 对照表逐条核）
□ GPL/AGPL 条目：包内已有《SOURCE-获取方式.txt》+ 许可证全文
□ Apache-2.0 条目：有 NOTICE 的已随包携带
□ 平台敏感词自检：文章 + 标题 + 封面 + 网盘分享页文件名
□ 包内无内部备注信息（曾发生过把 notes 写进正文的事故）
□ 联系方式已在文章与随包说明里公开
□ 若为「只介绍」类：**没有**配置关键词自动回复链接
□ 已判定条目属 **分发类 / 介绍类**（§3.4），且文章、关键词、网盘三处动作一致
□ 已留档：sha256、对应版本 tag、核验日期
□ 随包材料已跑 `node scripts/make-source-note.mjs --check` 且**退出码为 0**（`out/source-notes/CHECK.md` 无阻塞项）
```

## 七、责任分工与巡检节奏（建议）

| 事项 | 频率 | 输出 |
|---|---|---|
| 后台留言 / 邮箱巡检 | 每日 2 次（早/晚） | 有无新通知 |
| 关键词自动回复链接可用性 | 每周 | 失效链接清单 |
| 已发布条目的上游授权变更复查 | 每月（可挂版本巡检脚本一起跑） | 授权变更清单（如上游改协议 → 立即下架） |
| 争议档完整性抽查 | 每季度 | 缺口清单 |

> ⭐ **授权会变**。免费软件转商业、开源项目改许可（如 source-available 化）都真实发生过。**月度复查**是这套流程里唯一能防住「昨天合规、今天不合规」的环节，不要省。
