# 开源软件公众号 · 运营方案与流程设计

> 2026-10-08 · 内容方向：**实用工具 / 效率软件** + **设计创作类**
> 定位：把 GitHub 上的开源项目，做成「中文能看懂、下得到、还能长期跟上版本」的分享号
> 关联：本方案与现有网盘仓、采集器、台账体系**可复用**（见第 10 节）

---

## 0. 一页速览

| 项 | 结论 |
|---|---|
| **一句话定位** | 面向「不会翻 GitHub、看不懂英文文档」的人，做开源软件的**中文落地服务**：讲清楚、给直链、管版本 |
| **和闲鱼路线的关系** | **互补，不是替换**。闲鱼受平台风控和侵权投诉双线约束；开源路线授权清晰、可核验、无 IP 风险，是更可持续的正面战场 |
| **差异化三角** | ① 中文部署说明 ② 网盘直链 ③ **长期版本维护** —— 前两个别人也能做，第三个是真正的护城河 |
| **内容配比建议** | 实用工具/效率软件 : 设计创作类 ≈ 7 : 3（实测效率工具涨粉快，设计类用户粘性高、更愿意留言互动） |
| **一票否决红线** | 有「破解/激活/去授权」字样 · 协议属限制分发类 · 代码开源但内置资源另授权 · 无 LICENSE · 项目本身是盗版分发工具 |

**核心判断：这个号的价值不在于"介绍软件"，而在于"你替读者把踩坑的部分做完了"。** 纯搬运 GitHub Trending 的号已经很多且同质化；能活下来的都是愿意做脏活的。

## 1. 定位与读者

### 读者画像（决定文章写法）

| 类型 | 特征 | 他们真正想要的 |
|---|---|---|
| 普通用户 | 不会命令行、怕装坏电脑、英文吃力 | 「下载解压就能用」+ 出问题怎么办 |
| 效率党 | 会折腾，但懒得读文档 | 和现有工具比强在哪、有没有坑 |
| 设计/创作人 | 对效果敏感、关心硬件 | 效果对比图、配置要求、素材授权 |

> ⚠️ **设计创作类要额外注意**：这类软件常内置商业字体、图标、预设素材或模型权重，**代码协议管不到这些资源**。是本方案里最容易出事的一类，核验时优先级最高（见第 4 节 F 类）。

### 不做什么（一票否决）

- ❌ 破解版、激活版、去广告版、去授权版 —— 任何形态都不碰
- ❌ 协议为 source-available / 限制商用 / 限制再分发的项目
- ❌ 代码开源但仓库内资源授权不明的
- ❌ 本身用于分发盗版内容的工具

## 2. 全流程总览

```
① 发现 → ② 选品打分 → ③ 授权核验 → ④ 打包入库 → ⑤ 成文 → ⑥ 发布分发 → ⑦ 版本回访
                                                              ↑                    │
                                                              └──── 台账驱动 ───────┘
```

| 环节 | 频率 | 产出 | 卡点 |
|---|---|---|---|
| ① 发现 | 每周 1 次批量 | `candidate` 池 | 别每天刷信息流，会被牵着走 |
| ② 选品打分 | 随发现 | `verified` 候选 | 用「能不能下载就能用」当主判据 |
| ③ 授权核验 | 每个项目 | 核验记录 + 结论 | **最关键的闸门，不通过不许打包** |
| ④ 打包入库 | 通过核验后 | 网盘目录 + 校验值 | 优先用官方预编译产物 |
| ⑤ 成文 | 每周 1–3 篇 | 文章 + 封面 | 套固定骨架，别每篇重新想结构 |
| ⑥ 发布分发 | 成文后 | 群发 + 关键词自动回复 | 外链规则要实测 |
| ⑦ 版本回访 | 按月批量 | 更新包 + 更新推文 | 靠台账，不靠记忆 |

## 3. 环节一：发现与选品

### 3.1 发现渠道（按质量排序）

| 渠道 | 说明 | 适合 |
|---|---|---|
| **GitHub Topics** | `topics/awesome`、`topics/self-hosted`、`topics/design-tools`、`topics/productivity` | 最稳定，分类清晰 |
| **GitHub Trending** | `?since=daily` / `weekly`，可带语言筛选 | 热点补充 |
| **awesome 系列清单** | `awesome-selfhosted`、`awesome-mac`、`awesome-windows`、`awesome-design` | 已被人工筛过一轮，质量高 |
| **仓库内的 Related / Dependencies** | 已收录项目的上下游 | 垂直深耕，读者群重叠 |
| **上游 Release 的 Contributors** | 常能发现同类项目 | 冷门好物 |
| **Hacker News / r/selfhosted / r/opensource** | 国外社区 | 抢时间差 |

> 💡 **建议**：每周固定一个时段批量扫，一次收 20–30 个进 `candidate` 池，然后集中打分。散着看会导致「看着都好，一个都没做」。

### 3.2 选品打分（针对你的读者）

| 维度 | 加分 | 减分 |
|---|---|---|
| 界面 | 有 GUI | 纯命令行（普通用户直接劝退） |
| 安装 | 有官方预编译产物（exe/dmg/AppImage） | 需要自己 build / 配环境 |
| 体积 | < 500MB | > 2GB（下载体验差、网盘成本高） |
| 语言 | 有中文或多语言 | 纯英文界面 |
| 活跃度 | 近 6 个月有 release | 停更 > 1 年 |
| 热度 | Star 增长、话题讨论 | 无人问津 |
| 痛点 | 能一句话说清解决什么问题 | 需要解释半天才有感觉 |

**建议门槛**：GUI + 有预编译产物 + 有中文界面 → 三个都满足 = 主推；缺一个 = 备选；缺两个 = 放弃。

## 4. 环节二：授权核验（整个流程最关键的闸门）

### 4.1 协议分层表

| 层 | 协议 | 可否打包分发 | 处理方式 |
|---|---|---|---|
| **A** | MIT · BSD-2/3-Clause · Apache-2.0 · ISC · MPL-2.0 · GPL-2.0/3.0 · LGPL-2.1/3.0 · AGPL-3.0 | ✅ 可以 | 打包 + 随包附 LICENSE + 保留版权声明 |
| **B** | CC0 · CC-BY · CC-BY-SA（素材/文档类） | ✅ 可以 | 需按要求署名 + 附协议链接 |
| **C** | CC-BY-NC · CC-BY-ND（禁商用/禁演绎） | ⚠️ 视情况 | 公众号若有任何商业变现 → 不打包，只做介绍 + 原链 |
| **D** | BSL 1.1 · Elastic License 2.0 · SSPL · Commons Clause · PolyForm | ❌ 不可以 | 非 OSI 开源。视为商业软件，**只介绍不打包** |
| **E** | 无 LICENSE 文件 / "All rights reserved" | ❌ 不可以 | 默认保留全部权利，**不打包** |
| **F** | 代码 A 类，但内置资源（字体/图标/模型权重/预设）另有授权 | ⚠️ 需拆分 | 逐项核对，**剔除受限资源后**再打包 |

### 4.2 核验动作清单（每个项目必跑）

1. 读仓库根目录 `LICENSE` / `LICENSE.md` / `COPYING` / `COPYING.LESSER`，确认 SPDX 标识
2. 读 README 的 License 段落，**看有没有补充限制**（"non-commercial"、"no redistribution"、"for personal use only"）
3. 检查 `LICENSES/` 目录或多个协议并存的情况（常见于"代码 MIT + 素材 CC-BY-NC"）
4. 单独检查 `assets/` `fonts/` `icons/` `models/` `presets/` `samples/` 目录
5. 看 Releases 页产物是否捆绑了闭源组件（商业 SDK、专有驱动、第三方二进制）
6. 若是 fork → **必须同时满足上游协议**，且注意上游是否已变更协议
7. 查 `LICENSE` 文件内容里的实际年份与主体是否与项目一致（有些是模板没改）

### 4.3 特别提醒（三个高频踩坑点）

**① GPL 家族 ≠ 可以随便分发**
GPL-2.0/3.0、LGPL、AGPL 允许再分发，但附带**义务**：分发时必须提供对应源码（或明确的源码获取方式）+ 完整保留许可证文本。所以 GPL 项目的包里要放 `LICENSE` 和 `SOURCE-获取方式.txt`，不能只给二进制。

**② Apache-2.0 要保留 NOTICE**
如果仓库里有 `NOTICE` 文件，分发时必须一并携带。

**③ AI 类项目：代码和权重是两回事**
大量 AI 项目的代码是 MIT/Apache-2.0，但**模型权重**单独用 CC-BY-NC 或自定义协议。设计创作类工具（AI 放大、AI 抠图、AI 生成）最容易撞上这一条。**权重协议单独看，不要跟着代码协议走。**

### 4.4 核验记录格式

每个项目留一条这样的记录（写进台账）：

```
project:       项目名
repo:          https://github.com/owner/repo
license_spdx:  MIT                    # 仓库声明的 SPDX
license_file:  LICENSE                # 实际读到的文件
extra_terms:   无 / 见 assets/fonts/README.md（商业字体，已剔除）
resources_ok:  ✅ 已剔除受限资源
checked_at:    2026-10-08
checked_by:    人工
verdict:       PASS / PASS_WITH_CHANGES / REJECT
note:          打包版已移除内置字体，其余为 MIT
```

> **核验结论要冻结留档**。未来有人投诉时，"我核验过、核验结论是什么、依据是什么"就是你的证据链。

## 5. 环节三：打包与网盘

### 5.1 打包原则

| 原则 | 说明 |
|---|---|
| **优先官方产物** | 直接下 Releases 里的预编译包，**不要自己 build**（构建引入不可控，也可能违背协议） |
| **必须校验** | 下载后核对官方发布的 sha256 / GPG 签名，把校验值一起放进目录 |
| **形态优先级** | 绿色/便携版（解压即用） > 安装包 > 源码（仅附编译说明） |
| **不二次修改** | 不改二进制、不去水印、不替换资源。要改就改**说明文档**，不改程序 |
| **授权随包** | LICENSE 文件 + 授权说明放进包内与网盘目录，做到「脱离文章也能自证合规」 |

### 5.2 网盘目录结构（复用现有三层规范）

沿用 `仓/待售/软件/` 下的既有约定，**软件名 → 平台档 → 形态**，不超过 3 层：

```
开源软件/
└── 项目名/
    ├── 项目名 - windows版/
    │   ├── 便携版/
    │   │   ├── 项目名 1.2.3 中文便携版.zip
    │   │   └── 项目名 1.2.3.sha256
    │   └── 安装版/
    │       └── 项目名 1.2.3 官方安装包 (x64).exe
    ├── 项目名 - mac版/
    │   ├── 项目名 1.2.3 (Apple芯片).dmg
    │   └── 项目名 1.2.3 (Intel).dmg
    └── 授权说明/
        ├── LICENSE
        └── 本包说明.txt      ← 来源仓库 / 协议 / 核验日期 / 是否修改过
```

**命名规范沿用现有约定**：版本号写进文件名、架构写清楚（`(x64)` / `(Apple芯片)` / `(Intel)`）、Mac 侧只分芯片不分便携/安装。

> ⚠️ **名称同样要避开平台敏感词**：`破解` `免费` `永久` `全网最低` `可商用` —— 分享页面读者能看到，且公众号同样有内容审核。要表达同义时用 `开源版` `社区版` `便携版` `直接下载`。

### 5.3 随包《本包说明.txt》模板

```
项目名称：XXX
原始仓库：https://github.com/owner/repo
授权协议：MIT License（全文见同目录 LICENSE）
核验日期：2026-10-08
本包来源：官方 Release v1.2.3 的 xxx-win64.zip，未做任何修改
校验值：  sha256 = ....................
分发说明：本包依据 MIT 协议分发，著作权归原作者所有。
         如权利人认为本分发不当，请联系 <你的联系方式>，我们将立即下架。
```

## 6. 环节四：成文（固定骨架）

### 6.1 文章结构（每篇套用，别重新设计）

| 区块 | 作用 | 要点 |
|---|---|---|
| **封面** | 决定打开率 | 项目名 + 一句话定位 + 平台图标，风格统一 |
| **① 一句话定位** | 3 秒说清是什么 | ≤ 30 字，不堆术语 |
| **② 它解决什么问题** | 建立需求共鸣 | 场景化，2–3 句。写「你可能遇到过……」 |
| **③ 核心亮点** | 决定读完率 | 3–5 条，**必须配截图/GIF**，设计类要有效果对比图 |
| **④ 原作者 & 仓库** | 导流回原项目 | 明确写「觉得好用请去给作者点 Star」，附仓库地址 |
| **⑤ 授权协议说明** | 合规 + 建立信任 | **固定区块**，模板化。写清协议名 + 你的分发依据 |
| **⑥ 支持系统** | 降低误下 | 表格：Windows / macOS(Intel·Apple) / Linux / Docker / 其他 |
| **⑦ 安装部署** | 你的核心竞争力 | 分平台、步骤化、带截图。设计类补硬件配置要求 |
| **⑧ 常见问题** | 减少后台咨询 | 3–5 个高频问题（打不开、被杀软报毒、缺依赖） |
| **⑨ 版本更新记录** | 体现长期维护 | 本文版本 vs 上篇版本的变化 |
| **⑩ 获取方式** | 转化 | 后台回复关键词 / 阅读原文 |

### 6.2 授权声明固定区块（直接复制）

```
【关于授权】
本项目 <项目名> 采用 <协议名> 开源协议，原始仓库：<仓库地址>。
本公众号所做的整理工作为：中文说明编写、安装流程梳理、下载包转存。
软件著作权归原作者所有。本文不提供任何修改版、破解版或去授权版。
如需商用，请自行前往原始仓库确认协议条款。
如权利人认为本文或所提供下载存在问题，请通过 <联系方式> 告知，我们将第一时间处理。
```

### 6.3 按方向调整信息密度

| | 实用工具 / 效率软件 | 设计创作类 |
|---|---|---|
| 重点区块 | ⑦ 安装部署、⑧ 常见问题 | ③ 效果亮点、⑥ 硬件要求 |
| 必备素材 | 安装步骤截图、界面图 | **前后对比图**、性能实测数据 |
| 要写清 | 是否需要管理员权限、是否需关闭杀软 | CPU/GPU/显存/内存要求、是否支持 Apple 芯片 |
| 常见坑 | 缺运行库、中文乱码 | 显卡驱动、加速后端（CUDA/Metal）选择 |

## 7. 环节五：发布与分发（公众号平台规则）

### 7.1 主体选择（建议早点定）

| 主体 | 优势 | 限制 |
|---|---|---|
| 个人 | 注册快 | 类目受限、**无法开通微信支付**、部分商业化路径走不通 |
| 个体户 / 企业 | 类目完整、可挂小程序/支付、可认证 | 需营业执照，注册稍慢 |

> 如果未来打算做付费社群、会员、打赏之外的变现，**建议直接上个体户/企业主体**，否则后面迁移很麻烦。

### 7.2 外链怎么放

微信对外链的管控会调整，实操上分两层：

- **正文里**：放 GitHub 仓库地址是常规做法；但 GitHub 在微信内打开偶有限制，建议发布前**用另一个号实测一遍**，必要时在文中说明"复制到浏览器打开"。
- **网盘链接**：**不要直接贴正文**。走「后台关键词自动回复」是行业通行做法 —— 读者回复关键词，自动回复里给链接。好处是：链接可随时更换、失效了改一处就行、也不容易被判营销导流。

> 💡 关键词设计：`项目名` 或 `项目名简写` 单一关键词即可，别搞复杂暗号（读者记不住）。

### 7.3 必须避开的平台红线

| 红线 | 说明 |
|---|---|
| **诱导分享** | 不能写「转发到朋友圈才能获取」「集赞领取」 |
| **侵权内容** | 发布破解/外挂/盗版内容会被处理，正规开源软件不在此列 |
| **原创声明** | 你自己写的介绍文可以标原创；**软件本身不能标原创** |
| **绝对化用语** | 「最强」「第一」「永久免费」在广告法语境下有风险 |
| **下载包安全** | 被举报含恶意代码后果严重 → 校验值 + 不二次修改是自保 |

## 8. 环节六：版本跟踪与回访

这是「定期跟踪更新版本」这个承诺能不能兑现的关键。**靠台账，不靠记忆。**

### 8.1 回访策略

| 项目类型 | 回访节奏 | 动作 |
|---|---|---|
| 活跃项目（月更以上） | 每月检查 | 有新版本 → 更新包 + 更新网盘 + 发更新推文 |
| 稳定项目（季更） | 每季度检查 | 同上 |
| 停更项目 | 半年检查 | 标注「已停更」，或在文章里补一句说明 |
| 重大版本（major） | 立即 | 单独一篇；注意升级可能不兼容 |

> 💡 **汇总型推文比每版一篇更省力**：《本月开源软件更新合集》一个月一篇，把十几个项目的更新打包说清楚。既兑现了"持续维护"的承诺，又不消耗产能。

### 8.2 旧版本保留策略

- 至少保留**上一个版本**（读者回退用）
- 网盘目录只保留最近 2–3 个版本，更老的清掉（省空间也避免混乱）
- 文章里的「版本更新记录」区块累积保留，不删

### 8.3 网盘链接巡检

沿用你现有巡检脚本的思路：定期检查所有分享链接有效性，失效告警。
**链接失效是这类号最伤信任的事** —— 读者点进去打不开，直接取关。

## 9. 台账设计

对齐现有 `.listings.json` 的思路，单独建一份 `projects.json`（或表格），每个项目一条：

```
id                 项目唯一标识
name               项目名
repo_url           https://github.com/owner/repo
upstream_fork      是否 fork 自别的项目（是则填上游）
license_spdx       协议 SPDX 标识
license_note       补充限制说明 / 已剔除的受限资源
license_verified_at 核验日期
verdict            PASS / PASS_WITH_CHANGES / REJECT

latest_tag         最新版本号
latest_checked_at  上次检查版本的时间
last_article_ver   成文时的版本号
article_url        对应文章链接
update_policy      major / minor / patch / all

platforms          [win, macos-arm64, macos-intel, linux, docker, web, android]
package_type       [portable, installer, source, docker]
package_size_mb    体积
mirror_links       { baidu: "...", quark: "..." }
keywords           公众号关键词（用于自动回复配置）

stars              Star 数
trend_score        热度评分
status             candidate / verified / published / watch / dropped
notes              备注
```

**状态流转**：`candidate` →（核验通过）→ `verified` →（成文发布）→ `published` →（持续跟踪）→ `watch`
核验不通过直接 `dropped`，并记录原因（避免半年后又捡回来重复核验）。

## 10. 与现有基建的复用关系

| 现有资产 | 在本方案里怎么用 |
|---|---|
| `仓/待售/软件/` 三层目录规范 | **直接沿用**，公众号侧只是多一个"授权说明"目录 |
| 网盘目录工具 `npm run soft:tree` | 复用 `init` / `inspect` / `rename`，建号初期批量建目录 |
| 命名规范（版本号进文件名、架构标注、避开敏感词） | 完全复用 |
| 台账思路（`.listings.json`） | 换成 `projects.json`，字段按第 9 节设计 |
| 巡检脚本习惯（`watch:tunnel --heal`） | 复用同一套思路做网盘链接巡检 |
| 合规闸门思路（`publish-guard.ts`：先体检再放行） | 复刻成「核验闸门」：verdict 不为 PASS 不许进打包环节 |
| 版本跟踪的 Crypto 校验习惯 | 直接用于官方产物的 sha256 校验 |

> **一句话**：你在闲鱼那套流水线里沉淀的「台账驱动 + 闸门前置 + 巡检兜底」，是这套方案能跑起来的真正底座。差的只是把"平台风险闸门"换成"授权核验闸门"。

### GitHub 数据获取（可选自动化）

现有栈是 Node + TS，接 GitHub API 很直接：

```
GET /repos/{owner}/{repo}              → license.spdx_id, stargazers_count, pushed_at
GET /repos/{owner}/{repo}/releases/latest → tag_name, assets[]（文件名/大小/下载地址）
GET /repos/{owner}/{repo}/license      → license 全文
GET /search/repositories?q=...&sort=stars → 发现候选
```

- ⚠️ **必须带 Token**：未认证 60 次/小时，认证后 5000 次/小时
- ⚠️ **Trending 无官方 API**，需要爬页面或走第三方接口
- 建议：先做"版本巡检"这一个自动化动作（对比台账 `latest_tag` vs 线上最新），收益最高、实现最简单

## 11. MVP 起步路径

### 阶段一：验证（1–2 周）

1. 定向选 **10 个项目**（7 个效率工具 + 3 个设计工具）
2. 逐个跑第 4 节核验清单，产出核验记录
3. **手工**出 3 篇，套第 6 节骨架，验证：打开率、读完率、后台关键词回复量
4. 同步测一遍**外链在微信内的实际行为**（正文直链 / 阅读原文 / 关键词回复三种方式）

> 目标不是产量，是验证"读者到底吃不吃这套结构"。

### 阶段二：固化（1 个月）

1. 台账上线（第 9 节字段），10 个项目全部建档
2. 文章骨架与授权声明区块固化为可复用模板
3. 封面视觉定稿（统一风格，后续套版）
4. 打包流程固化，网盘目录规范化

### 阶段三：半自动化

1. GitHub 版本巡检脚本上线 → 台账自动对比
2. 文章骨架生成（人工只填亮点、截图、部署细节）
3. 月度更新合集推文机制跑起来

## 12. 风险清单

| 风险 | 后果 | 应对 |
|---|---|---|
| 误收了限制分发协议的项目 | 侵权投诉、封号 | 第 4 节核验清单 + verdict 冻结留档 |
| 内置资源授权没查（字体/模型权重） | 被字体公司或模型方追责 | 设计创作类**逐项目**查资源目录 |
| 上了 GPL 项目但没给源码 | 违反协议义务 | GPL 家族必须附源码获取方式 |
| 网盘链接失效 | 读者取关 | 定期巡检 + 告警 |
| 版本跟踪断档 | 承诺落空、失去差异化 | 台账驱动 + 月度合集 |
| 正文直接贴网盘链接 | 判营销导流 | 走关键词自动回复 |
| 下载包被杀软误报 | 信任崩塌 | 官方原包不修改 + 提供校验值 + 常见问题里说明 |
| 个人主体限制商业化 | 后期迁移麻烦 | 早期就定主体 |
