### 重新核实的鉴权事实

- 先前把 `apiVersion=v3` 等同于 `m.goofish.pro` 的记录有误。
  `ajax.js` 的 `_0xe99c83` 对 v3 请求实际使用 `getApiDomain('v1')`，即 **`https://api2.goofish.pro`**，
  同时将请求内容类型设为 JSON。对 `m` 的同一路径 POST 实测 HTTP 405。
- 商品配置 `info/save` 是 JSON POST，查询串 `channel=1&version=3.71.1`。
  官方 WebAssembly `httpSinWithKey(path,query,method,body,encryptFlag)` 生成 `X-Content-Security`。
  请求路径不含域名与查询串；body 使用实际发送的原文，签名和网络传输字节必须一致。
- `consign/info`、`consign/save` 当前网页方法默认 `encrypt=0`，并非所有请求都加密。
  登录 `qrcode/create`、`qrcode/check`、`token/create` 使用 AES-256-ECB 默认密钥方法加解密，
  签名对象是实际发送的密文，标记 `encrypt=1`。
- 账号令牌放 `Authorization`，不加未经确认的 Bearer 前缀。
  已用纯 Node.js + 官方 WASM 请求 `consign/info`：HTTP 200、code=401（登录过期）；
  同环境加密请求 `qrcode/create`：HTTP 200、code=0，返回二维码字段。
  最初仅证明签名与加密请求可用；登录后的真实只读验证结果见本节末尾，真实保存尚未验证。
- 本次上述请求没有 Cookie。旧记录把签名失败推断成必须 Cookie/设备指纹，没有充分证据。
  本轮后续登录态查询与预演已在无 Cookie 条件下通过。

### 批量入口（10-20 下午补齐）

```sh
# 1) 只读预演：逐件 info + 货源精确查询 + 生成载荷，永不写
npm run consign:api -- plan --refresh [--codes-file out/xxx.json] [--limit N] [--template-product <id>]
# 2) 写：必须显式 --yes，且只认同一批次的 plan 报告
npm run consign:api -- apply --batch out/consign-batch-plan.json --yes
```

- `plan` 用 `allowSave:false` 的客户端，`/v1/kami/consign/save` 在传输层就不可达，不是"约定不调"。
- `apply` 只从报告读行，不重新构建目标；报告行必须带预演时的 `before` 快照，且顺序/商品 ID 完全一致。
- 逐件保存前 `saveSingle` 会重新 `info` 核对快照、`item_id/authorize_id`、货源价格（元→分）与库存。
- 串行、写间隔 ≥3.5s；任一写失败立即停止，并对该件读回记录线上状态；任何写都不重试。
- `--template-product` 可省略：会自动在本批里找一件已正确配置的；本批全没配时必须显式传。
