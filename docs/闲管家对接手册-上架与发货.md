# 闲管家对接手册：上架 + 自动发货（可移植版）

> 目标读者：要把「闲管家上架 + 自动发货」搬到另一个项目的开发者。
> 本文只写**本项目实测验证过**的逻辑；没验证的会明确标注「未验证」。
> 最后更新：2026-10-20。源码位置以 `bdpan-goofish` 路径给出，便于对照抄。

---

## 0. 先理解：闲管家有**三套**互不相通的体系

这是整个对接里最容易搞错的地方。三套体系的域名、鉴权、用途完全不同，**签名不能混用**。

| 体系 | 域名 | 鉴权 | 用途 | 你会遇到什么 |
|---|---|---|---|---|
| **A. 开放平台** | `https://open.goofish.pro` | AK/SK + MD5 签名（query 串） | **商品上架**、订单查询、物流发货、卡种/卡密 | 官方文档齐全；**没有**商品发货设置接口 |
| **B. 虚拟货源** | 由**你**提供（本项目 `https://xgj.fmkj.top`） | 另一套 MD5 签名 | 闲管家**反向调用你**：查商品、下单取卡 | 我们在实现「货源方」那一侧 |
| **C. 网页后台内部接口** | `https://api2.goofish.pro` | 登录态 token + 官方 WASM 签名 | **商品侧发货设置**（把商品绑到货源商品） | 官方文档没有；靠官网自己的 JS/WASM |

```
买家拍下
  → 闲管家查「商品发货设置」（体系 C 里配的那条记录）
  → 按 goods_no 找到货源商品
  → POST 你的网关 /goofish/order/purchase/create   （体系 B：闲管家 → 你）
  → 你返回 card_items
  → 闲管家标记发货 + 把卡密发给买家
```

**关键认知**：只做 A（上架）不会自动发货；只做 B（网关）也不会，因为商品上没有「发货设置」这条记录。**A + B + C 三件齐了才会自动发。**

## 1. 体系 A：开放平台（上架主体）

### 1.1 接入准备

1. 闲管家后台订购 **ERP 专业版 / 铂金版**（高级版**不能**创建应用）
2. 创建应用，拿到 **AppKey / AppSecret**
3. **应用上线**（未上线调用会 404 / 返回 HTML）
4. 上架用应用类型选「进销存」；发货相关（卡种绑货源）要用「虚拟货源」应用 —— 两者 AppKey 不同，**别混**

### 1.2 签名（逐字照抄，错一个字符就是 401）

```js
// sign = md5( "appKey,bodyMd5,timestamp,appSecret" )
// 商务对接模式才插 sellerId：md5( "appKey,bodyMd5,timestamp,sellerId,appSecret" )
const bodyString = JSON.stringify(body);          // 压缩 JSON，无空格，参数不排序
const bodyMd5    = md5(bodyString);
const sign       = md5([appKey, bodyMd5, timestamp, appSecret].join(','));
```

请求形状：

```
POST https://open.goofish.pro/api/open/xxx/yyy?appid=<AppKey>&timestamp=<秒>&sign=<sign>
Content-Type: application/json; charset=utf-8
Body: <bodyString 原文>
```

> ⚠️ 签名参数叫 **`appid`**（小写，放 **query 串**），不是请求头，也没有 `appVer`。
> 网上有些教程（如 `thefreelight/xian-guanjia`）用的是虚拟货源那套六参数签名，**用于开放平台必然 401**。

官方测试向量（自检用）：

```
appKey=203413189371893  appSecret=o9wl81dncmvby3ijpq7eur456zhgtaxs
timestamp=1636087298    body={"product_id":"219530767978565"}
bodyMd5=2608f2139cca8755cabf25209251e549
sign=c26c8a48809141f3dd80bd9b9ddb41ea      ← 对不上就是实现错了
```

源码：`packages/goofish-adapter/src/sign.ts`（签名）、`client.ts`（传输）、`endpoints.ts`（全量路径）

### 1.3 上架流程（已验证，208 件在售）

```text
① product/category/list  → 拿 channel_cat_id（闲鱼类目）
② product/pv/list        → 拿类目必填属性
③ product/create         → 创建草稿（注意下面必填）
④ product/publish        → 上架
⑤ product/detail         → 读回，只认 item_id > 0 才算成功
```

**`product/create` 必填**（`draft.ts:validateDraft`）：

| 字段 | 说明 |
|---|---|
| `item_biz_type` / `sp_biz_type` | 商品类型 / 行业类型，虚拟商品有对应枚举 |
| `channel_cat_id` | 闲鱼类目 ID |
| `price` | **单位是分**（9.9 元 → `990`），写成元就是差 100 倍 |
| `stock` | 非负整数 |
| `publish_shop[]` | 至少一个，含 `user_name`（**闲鱼会员名**）、`title`、`content`、`images[]`、省市区 |
| `images[]` | **必须是公网 http(s) URL**。官方没有图片上传接口，得自己图床 |

### 1.4 上架踩过的坑（全部是钱换来的）

1. **「成功」不等于上架**：`product/publish` 返 ok 只是提交时刻；判成功**只认 `item_id > 0`**。异步，等 60~900 秒再 `product/detail`。
2. **换店 / 换类目必须重建**：`product/edit` 对 `publish_shop` 是**追加**语义，不是替换 → 一条商品会挂两个店 → 之后 publish 永久报「每个商品只能发布1个闲鱼店铺」（code 100001，真因只在 `msg`）。
3. **发布失败本身会污染商品**：每次失败尝试都会往 `publish_shop` 追加一条。所以别反复探测「卡住的草稿」，先枚举确认是干净草稿。
4. **下架重上要算额度**：曾用 `--every 20` 秒推 275 条 → 店铺被判异常、405 个在售被下架。**间隔 ≥300 秒**，分批。
5. 标题 ≤30 字（数字/特殊字符各占 2 位）；单店在售触顶约 500 件。
6. 所有接口合计 **QPS 限制 10**，客户端要自己限流。

### 1.5 订单与发货（开放平台侧）

| 用途 | 路径 | 备注 |
|---|---|---|
| 拉订单 | `/api/open/order/list` | **列表即全字段**，别逐单再调 detail |
| 订单详情 | `/api/open/order/detail` | |
| 订单卡密 | `/api/open/order/kam/list` | 空 = 我方从未发过货 |
| 无需物流发货 | `/api/open/trade/logistics/dummy/send` | `send_way: 1` 虚拟 / `2` 无需物流 |

**实测状态码（只认这个表）**：

| `order_status` | 含义 | 判据 |
|---|---|---|
| **12** | **待发货**（已付款未发货） | `consign_time=0` |
| 21 | 已发货 / 待收货 | `consign_time>0`、`consign_type=2` |
| 22 | 交易完成 | `confirm_time>0` |
| 23 | 退款相关 | `refund_status` 多为 5 |
| 24 | 已关闭 | `consign_time=0` |

> ⚠️ 我们曾把 21 当成「待发货」，导致欠单全漏 + 已发货单被误判。**判「未发货」只认 `consign_time=0`。**

> ⚠️ `dummy/send` **只是改状态，不带内容**。闲管家**不开放**给买家发消息的接口（官方明确「后续也没有开放的计划」）。所以「补发」= 后台标记 + 你自己把卡密私聊给买家。

### 1.6 退款口径（本项目定）

买家退款 → **直接同意退款，不作废已发出的链接**。`decideOrderAction` 的退款分支只返回「同意退款，保留分享链接」；`tests/refund-policy.test.ts` 锁住这条。

## 2. 体系 B：虚拟货源网关（你需要自己实现）

闲管家在「卡密仓库配置货源商品」和「买家下单」时会**请求你的服务**。不是全部都要实现——按需求选。

### 2.1 必须实现（否则后台保存就失败）

| 接口 | 路径（你定义的前缀 + 下列路径） | 关键返回 |
|---|---|---|
| 查询平台信息 | `/goofish/open/info` | `app_id` = **应用概况里的 AppKey**（整数）；`features.is_support_*` 三个布尔 |
| 查询商户信息 | `/goofish/user/info` | `balance` 必须 **> 0**，否则保存失败 |
| 查询商品列表 | `/goofish/goods/list` | `{ list, count }` |
| 查询商品详情 | `/goofish/goods/detail` | 见下 |

商品对象必填：`goods_no`、`goods_type`、`goods_name`、`price`（**分**）、`stock`、`status`（1 在架 / 2 下架）、`update_time`。

`goods_type` 枚举：**1 直充 / 2 卡密 / 3 券码**。

### 2.2 卡密发货额外需要

| 接口 | 路径 | 说明 |
|---|---|---|
| 订阅商品变更 | `/goofish/goods/change/subscribe` | ⚠️ 顺序是 `goods/list → subscribe → goods/detail`；**订阅失败整个配置流程中断** |
| 创建卡密订单 | `/goofish/order/purchase/create` | 闲管家调你取卡 |
| 查询订单详情 | `/goofish/order/detail` | 管家核验用 |

### 2.3 签名（**与开放平台完全不同**）

```js
// sign = md5( "app_id,app_secret,md5(body),timestamp,mch_id,mch_secret" )
//   app_id/app_secret = 闲管家给你的应用 AppKey/AppSecret
//   mch_id/mch_secret = 你给自己的商户号/密钥（填进「货源授权信息」）
const bodyString = JSON.stringify(body);   // 压缩 JSON，两端必须逐字节一致
const sign = md5([appId, appSecret, md5(bodyString), timestamp, mchId, mchSecret].join(','));
```

官方测试向量：

```
app_id=677859093659717  app_secret=wK63PxlOBaY9NoqMksLeZySzGIW25ifA
mch_id=100              mch_secret=o9wl81dncmvby3ijpq7eur456zhgtaxs
timestamp=1724414553    body={"goods_type":1,"goods_no":"12344532"}
→ sign=f8677927fd8421a75718e8cfaaf92221
```

源码：`packages/xgj-gateway/src/sign.ts`；自检 `npm run verify:sign-vs`

### 2.4 网关最容易踩的三个坑

1. **闲管家会先用 GET 探测你的接口**。你一率回 405 → 它判定「接口不可用」，真实订单根本不发过来。已知路径的 GET 必须回 `{"code":0,"msg":"OK"}`，POST 才验签。
2. **`goods/list` 慢一点后台就填不了**。我们曾对每个商品读一次大 JSON → 9.5 秒 → 下拉框超时。加 mtime 缓存后 60ms。
3. **`goods_type` 两边枚举不一致会静默过滤成空**：你标 `2`、它查 `1` → 列表空 → 报「获取货源商品失败」。本项目对 1/2 都放行。

### 2.5 下单接口的实现要点

```jsonc
// 闲管家 POST 给你
{ "order_no": "...", "goods_no": "BD-XXX", "buy_quantity": 1,
  "max_amount": 288,          // 商家可接受的最大成本（分），超过要返回 1202
  "item_id": 109..., "product_id": 180... }
```

- **幂等**：同一个 `order_no` 必须返回同一结果，不能再次扣卡（闲管家会重试）
- 商品不存在 → `1100`；下架 → `1101`；库存不足 → `1102`；金额超 `max_amount` → `1202`
- 同步返回成功时带 `card_items`，**不需要**再调 `notify_url`

源码：`packages/xgj-gateway/src/handlers.ts`

## 3. 体系 C：商品侧发货设置（最难的一块）

### 3.1 事实

- **开放平台没有这个接口**。官方全量 43 个接口里查无此项；实测 `open.goofish.pro/api/open/kami/consign/{save,info}` 等 6 个候选路径**全部 404**（对照组 `kami/kind/edit` 正常）。
- 网页端内部接口：`POST https://api2.goofish.pro/v1/kami/consign/{info,save}`
- 查询串固定 `?channel=1&version=3.71.1`
- 请求头：`Authorization: <登录 token>`、`X-Content-Security: <官方签名>`、`Content-Type: application/json;charset=utf-8`
- 历史教训：`m.goofish.pro` 是错的（HTTP 405）；只带 JWT 会报「安全验证失败-1」；**不需要 Cookie**（旧结论有误）

### 3.2 怎么拿到签名：复用官网自己的 WASM

不是仿造，是直接用官方运行的代码：

1. 下载 `https://www.goofish.pro/app_v3.71.1_<ts>.js` 和 `https://xgj-wasm.goofish.pro/utils.wasm.gz`
2. **校验 SHA-256 并固定**（版本一变就停止，不静默运行新代码）
3. 在 Node 的 `vm` 里跑提取出的加载器，得到 WASM 实例
4. 用它导出：
   - `httpSinWithKey(path, query, method, bodyString, encryptFlag)` → 签名字符串
   - `aes256EcbEncryptWithDefaultKey / DecryptWithDefaultKey`（登录接口用）

```js
// 客户端要点（scripts/lib/xgj-web-client.mjs）
const query = `channel=1&version=3.71.1`;
const body  = JSON.stringify(params);            // 签名对象 == 实际发送的字节
const sig   = runtime.httpSinWithKey(path, query, 'POST', body, 0);
await fetch(`https://api2.goofish.pro${path}?${query}`, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json;charset=utf-8',
             'X-Content-Security': sig, Authorization: token },
  body, redirect: 'error',
});
```

### 3.3 登录（扫码，无 Cookie）

```
POST /v1/user/login/qrcode/create   {login_way:3, qrcode_scene:'auth_login'}  ← 加密+签名
  → 出二维码，微信扫码
POST /v1/user/login/qrcode/check    {qrcode_token}     → login_status: 0 待扫 / 1 已扫 / 2 已确认 / 3 过期
POST /v1/user/login/token/create    {login_token, login_way:3, device_id:''}  → access_token
```

token 存本地，权限 600、原子写、拒绝软链。失效码：**61 / 401 / 2011**（收到就停，重新扫码，不要重放）。

### 3.4 保存发货设置：参数形状（已验证）

读 `consign/info`：

```jsonc
{ "send_type": 1, "product_id": 1800364302878213, "product_sku": 0 }
```

写 `consign/save`（**`product_id` 是数组**）：

```jsonc
{
  "send_type": 1, "send_dummy": 1, "send_limit_min": 1, "send_limit_max": 9999,
  "postscript": "", "send_statement": false, "ex_url_status": 0,
  "extra_config": "{\"refund_revoke\":{\"enable\":false},\"refund_restock\":{\"enable\":false}}",
  "send_rule": 1, "send_multiple": 1, "again_send": false,
  "template_id": 1787619864662213,
  "consign_id": 0,                       // 新建填 0；更新填原 consign_id
  "product_id": [1800364302878213],
  "product_sku": 0,
  "kind_way": 4,                         // 4 = 直接货源（本项目用这个）
  "kind_id": 0,
  "status": 1,
  "product_list": [{ "authorize_id": 1671498835378245,
                     "item_id": 1091045364278,
                     "product_id": 1800364302878213 }],
  "app_id": 1787570964481861,            // 虚拟货源应用的 AppKey（不是进销存那个！）
  "erp_id": 91,
  "goods_no": "BD-ARTCRAFT",
  "goods_name": "...",
  "goods_price": 288,                    // 分：货源 purchase_price（元）× 100
  "goods_stock": 9999,
  "adjust_price": { /* 原样带回，别改 */ }
}
```

**`kind_way` 的语义**：`2` = 关联卡种，`4` = 直接关联货源商品。本项目用 **4**（已真实成功一单）。

### 3.5 保存的 7 条硬规则

1. **不许猜默认值**：所有字段从一份**线上已启用、读回成功**的配置复制（`copy-a-live-working-config`），绝不自己填。
2. **不覆盖**：已有其他启用配置 → 保留原样跳过。已关联同一货源 → 幂等跳过。
3. **不改自动调价**：原 `adjust_price` 原样带回。
4. **元/分转换**：保存用分，货源 `purchase_price` 是元。
5. **保存后必须读回**：核对 `status=1`、`kind_way`、`app_id`、`goods_no`。只看到「成功」不算完成。
6. **写请求不重试**：超时/失败先停下读回，确认没落地再决定。
7. **限速**：写请求至少隔 **3.5 秒**，否则报「操作过于频繁」。

## 4. 上架 + 发货的完整落地顺序

```
【一次性配置】
1. 建开放平台应用（进销存）→ 上线 → 得 AppKey/AppSecret
2. 部署货源网关（体系 B），4 个必需接口 + 下单接口；确保 GET 探测回 200
3. 建虚拟货源应用 → 填「货源授权信息」：接口网关=你的域名，AppKey/Secret=你的 mch_id/mch_secret → 上线
   （上线时会请求 查询平台信息 + 查询商户信息，失败要逐项查地址/签名/返回类型）

【每个商品】
4. product/create → product/publish → 读回 item_id > 0
5. 卡种绑定：kami/kind/edit 写 app_id（虚拟货源应用） + goods_no（= 你的商品编码）
   ⚠️ app_id=0 会让 goods_no 被静默丢弃；服务端不校验商品存在 → 必须读回
6. 商品发货设置：consign/save（体系 C）→ 读回核对

【运行时】
7. 买家拍下 → 闲管家调你 /goofish/order/purchase/create → 你出卡 → 它发货
```

### 批量跑的正确姿势

- 先 `plan`（**只读**）：逐件 `info` + 货源精确查询 + 生成载荷，报告落盘
- 再 `apply`：**只从同一批次报告读行**，每件保存前重新 `info` 核对快照，串行、失败即停
- 灰度 1 件通过再放量
- 参考实现：`scripts/lib/consign-batch.mjs`、`scripts/consign-api.mjs`

## 4.5 已经打包好的网关：直接用，不用自己写

体系 B（闲管家反向调你）已经做成**可独立部署的包**：`packages/xgj-gateway/`。

```sh
cd packages/xgj-gateway
cp .env.example .env          # 填 4 个值
docker compose up -d --build  # 起来后把公网地址填进闲管家「货源授权信息 › 接口网关」
```

- **零运行时依赖**：打包成单个 `server.mjs`（29.8 KB），运行镜像里没有 node_modules
- **数据源可插拔**：默认 JSON 文件；要接你自己的库就实现 `GatewayStore` 接口
  （`createServer({ config, store })`），骨架见 `createMemoryStore()`
- **协议契约、错误码、部署坑**都写在 `packages/xgj-gateway/README.md`

如果你另一个项目只需要「上架」（体系 A）而不需要当货源方（体系 B），
那搬 `packages/goofish-adapter` 就够了，不需要这个网关。
