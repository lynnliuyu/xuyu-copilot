### 1.3 根因：上架和发货走了两条**互不相通**的轨道

闲管家有两套应用，方向正好相反（这是当初选型时的取舍）：

| 应用 | 类型 | 能做什么 | 不能做什么 |
|---|---|---|---|
| `bdmcp-xy-j` | 进销存 `erp` | **API 建商品 + 上架**（`/api/open/product/*`） | 发卡要自己写 |
| `bd-to-xy` | 虚拟货源 `virtual_source` | 下单时把卡密返给闲管家，**它自己发给买家** | **没有建商品接口**，必须人工在后台建商品并关联货源 |

现在的实际情况：

```
我们上架的 212 件  ──(进销存 API 直接挂到闲鱼)──>  闲鱼买家能拍
                                                      │
                                            买家拍下，订单进闲管家"进销存"
                                                      │
                                     ✗ 但这件商品不在"虚拟货源"体系里
                                                      │
                                     ✗ 闲管家不认识它 → 不会调我们的网关
                                                      │
                                              我们的网关全程沉默
```

所以这**不是配置错了，也不是网络不通**（`/goofish/ping` 一直是 405，健康）。是架构上两套东西没接起来。

> 补充证据：网关上 `purchase/create` 的 2090 条日志里，`order_no` 全是 `CHECK-DELIVERY-<时间戳>-<序号>`，
> 也就是 `npm run check:delivery` 自己造的单。一条真实订单都没有。

## 2. 发货的三条路（需要你选一条）

### 路线 A｜转到虚拟货源体系

人工在闲管家后台给每个商品"建一次商品 + 关联货源"，之后闲管家原生发卡，我们什么都不用做。

- ✅ 发货零维护，闲管家负责发给买家
- ❌ **每上新一个商品就要人工建一次**；虚拟货源不支持 API 上架，等于把已经跑通的自动化上架废掉
- 适合：只做 20~30 个精品，不值得为长尾维护

### 路线 B｜在进销存侧自建发货（**推荐**）

闲管家进销存已经有全套接口，只是我们没用：

| 接口 | 用途 | 现状 |
|---|---|---|
| `/api/open/order/list` | 拉订单 | 仅在 `endpoints.ts` 登记，**没写流程** |
| `/api/open/order/detail` | 订单详情 | 同上 |
| `/api/open/trade/logistics/dummy/send` | **无需物流发货**（`send_way` 1=虚拟发货 / 2=无需物流） | 同上 |
| `/api/open/order/kam/list` | 订单卡密列表 | 同上 |

一条最小的发货 worker 大约 200 行：轮询 `order/list` → 用 `goods_no` 匹配本地 `cards.json` → 取一条未用卡 →
调 `dummy/send` → 回写 `used/order_no`（幂等键就用闲鱼订单号）。

- ✅ 与现有 API 上架天然配套，**758 个商品全覆盖**，不用人工建商品
- ✅ 卡密池已经就绪（756 条真实链接），只差"点火"
- ❌ 要写代码 + 常驻进程；`dummy/send` 到底能不能把卡密文本发给买家，**必须先验一单**

### 路线 C｜先纯手工，验证需求

什么都不写，买家拍下后你手动去网盘取链接、在闲鱼发过去。

- ✅ 0 开发，今天就能开始卖
- ❌ 每单都要人盯；夜里/上班时的单会拖
- 适合：先确认「真有人买」，再决定要不要自动化

### 路线 D｜卡种绑商品（**已全自动，2026-10-19 实测通过**）

> 早前判断「绑定只能人工」是**错的**。`kami/kind/list` 返回的字段里有 `app_id` / `goods_no` /
> `goods_name`（旧文档没写、TS 类型也没定义），实测 `kami/kind/edit` 接受它们 ——
> 这就是后台「卡密仓库 → 发货 → 关联商品」的 API 版本。**不需要点后台。**

链路：`kami/kind/create`（建卡种）→ `kami/storage/create`（灌卡）→ `kami/kind/edit`（绑 `goods_no`）

- ✅ 三步全自动，工具 `scripts/kami-auto.ts`（`--dry` 预演 / `--apply` 真写 / `--rollback` 回滚）
- ✅ 绑好之后是**闲管家原生发卡**（连给买家的消息都由它发），零常驻进程
- ✅ 范围只跟"会卖的商品数"成正比 —— 近 90 天只有 **11 个商品**出过单，不是 758 个
- ❌ 新上商品要再跑一次脚本（一条命令，不用点）

**三个坑（都实测踩过）**
1. `app_id` 必须填 `1788532675364357`（本应用 `bdmcp-xy-j`）；**填 0 时 `goods_no` 被静默丢弃**
2. 服务端**不校验商品是否存在** —— 填假编号也"成功" ⇒ 脚本必须读回核对
3. 灌卡密有**长度上限**，整段买家文案会报「卡密长度超过限制」⇒ 必须拆成 `card_no`(链接) + `card_pwd`(提取码)

**已知未验证**：闲管家是按 `outer_id`（`BD-GFX-xxxx`）还是 `product_id` 匹配商品？
这次灰度绑的是 `outer_id`，需要后台看一眼或真下一单确认；不对就改填 `product_id`（脚本改一行）。

### 建议的执行顺序（按本轮实测修正）

**先止血 → 再给热销品上原生发卡 → 最后才考虑自建 worker。**

1. **今天**：把压着的 8 单人工补发掉（`npm run order:probe -- --copy` 直接给现成文本）。
2. **本周**：给近 90 天出过单的商品走路线 D —— `npx tsx scripts/kami-auto.ts --hot --apply`
   一条命令完成「建卡种 + 灌卡密 + 绑商品」，**不用在后台点**。已完成 1 个灰度（`BD-GFX-124840`），待验证发货。
3. **之后**：老品 `Codex安装包`（近 90 天 25 单，是当前第一销量）根本没进我们的资源体系 ——
   要么补进卡密池、要么继续人工。**这个得你定，因为资源可能不在网盘仓里。**
4. 路线 B（自建 worker）降级为**长尾兜底**：它只能解决"标记已发货"，发不了聊天内容，
   所以只在"商品太多、绑不过来"时才值得写。

⚠️ 路线 B 的那个未知点，本轮有了**强推断**（还没实测）：`dummy/send` 的参数只有 `order_no` + `send_way`（1=虚拟 2=无需物流），
**没有任何承载卡片内容的字段**；而闲管家 46 个接口里**也没有给买家发消息的端点**。
⇒ 它极可能只负责"标记已发货"，内容得另走 —— 自建 worker 天生只能做到"半自动"。
（真要验只能拿一笔真实订单试，`npm run order:probe -- --shape` 能先看请求体长什么样，不发。）
