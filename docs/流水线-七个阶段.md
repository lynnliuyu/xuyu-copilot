# 流水线：七个阶段

> 一句话：**网盘是仓库，资源站是橱窗，运营台是流水线，闲管家是收银台，网关是发货口。** 这五样不是同一个东西，其中三样现在都被人叫过「站点」。

本文件是**地图**，不是方案。它只回答「我现在在哪一步、这一步的入口是哪条命令」。

## 一、七个阶段与各自的入口

| # | 阶段 | 做什么 | 唯一入口 | 现状 |
|---|---|---|---|---|
| ① | **收集** | 从来源站点/仓库采集候选清单 | `npm run soft:423` · `soft:mac` · `soft:repack` · `fetch:free` · `gh:audit` · `gh:watch` | 6 个采集器，各自一条命令 |
| ② | **整理分类** | 归目录、归类、起中文名 | `npm run soft:tree` · `tree:netdisk` · `gen-soft-dirs.mjs`（**无入口**） | |
| ③ | **上网盘 + 建分享** | 传文件进网盘、建永久分享链接 | `npm run push:free` · `push:multi` · `push:license` · `share:netdisk` · `sandbox-share.mjs`（**无入口**） | |
| ④ | **回填站点** | 链接 + 封面写进站点数据 | `share:netdisk` → `netdisk-site/shares.json`；`media:netdisk` → `media.json`；`npm run site:netdisk` → `data.js` | 站点已有 **929** 条链接 / **795** 张封面 |
| ⑤ | **建条目 + 草稿** | 资源 → 资源条目 → 发布草稿 | `import-resources.ts`（**无入口**） | **755** 条资源，其中 **754** 条已带分享链接 |
| ⑥ | **发布** | 过体检 + 300s 节流，提交到闲鱼 | `drip-publish.mjs`（**无入口**） · `npm run republish` · `publish:queue` | 在售 **594** |
| ⑦ | **发货** | 买家拍单 → 出卡密 | `npm run card:sync` + 网关；**商品关联只能人工** | 见下方第二、三节 |

### ⭐ ③→⑦ 这一段**已经有编排器了**

`scripts/pipeline.mjs`（91 行）已经把「出链 → 建条目 → 出图 → 发布 → 灌卡密」串成一条链，注释里连两个隐式顺序依赖都写清楚了（`render-covers` 必须在 `import-resources` 之后，`card-sync` 必须在发布之后）。

问题只有一个：**它自己不是 npm 入口**，而且它调用的 5 个步骤里有 4 个也不是。所以「我想要一条命令跑完」这件事，代码早就写好了，只是没有发现它的路径。

## 二、「站点」有三个，各叫各的

| 该叫 | 目录 | 在哪 | 干什么 | 现在被叫成 |
|---|---|---|---|---|
| **资源站** | `netdisk-site/` | 本地静态文件，**尚未部署到公网** | 对外展示网盘资源 + 分享链接 | 「我的站点」 |
| **运营台** | `packages/xgj-admin` | 本机 `127.0.0.1:8790` | 资源条目、草稿、体检、发布护栏 | 「后台」 |
| **网关** | `packages/xgj-gateway` | 公网 → 本机 `8787` | 闲管家回调，从卡密池出卡 | 「站点」「服务」 |

⚠️ **自动发货不是资源站做的。** 买家拍单 → 闲管家**原生发货**（ADR-0001）→ 回调**网关** → 网关出卡密 → 闲管家把卡密发给买家。资源站是静态展示页，不接触任何订单。

⚠️ **「卡密仓库 → 闲鱼商品」的关联没有 API，只能人工点。** 这是官方流程（见 `GLOSSARY.md` 的「卡密仓库」），不是代码缺陷。

## 三、为什么「理不清」（三个可量化的原因）

1. **入口只覆盖一半。** `scripts/` 下 89 个可执行文件，只有 44 个有 npm 入口；**45 个没有**（其中 3 个是共享库，42 个是可跑的脚本）。**流水线的关键步骤有一半落在这个「无入口」集合里** —— 想跑它们只能靠记得文件名。
2. **三个不同的东西共用一个称呼**（见上表）。说「站点」时无法判断指哪一个。
3. **「条目」这个词是一个，代码里是两个。**
   - 站点条目 ← `out/netdisk-index.json`，来自**扫描网盘目录树**
   - 闲鱼条目 ← `drafts/.resources.json`，来自**采集器产物**
   两者共用同一条网盘分享链接，但**互不引用**。所以「上传条目到站点」和「对接闲管家发布」看起来像一条链的两端，实际是两条平行线。

## 四、同一段逻辑有多个入口的地方

| 步骤 | 入口 | 备注 |
|---|---|---|
| 发布 | `drip-publish.mjs` · `republish` · `publish:queue` · `artcraft-publish.ts` · 运营台「批量发布」按钮 | 五条，其中两条仍把「接口受理」当「已上架」 |
| 上网盘 | `push:free` · `push:multi` · `push:license` · `sandbox-share.mjs` | 四条，路径解析各写一份 |
| 发布后灌卡密 | 只有 `drip-publish.mjs` 做 | 其余四条路径不做 → 卖了发不出货 |

## 五、所以：这些是「收口」，不是「重构」

按顺序，**都不动业务逻辑**：

1. **补 npm 入口** —— 给流水线里那 42 个无入口脚本加别名（只改 `package.json`，不改代码）。
2. **公开编排器** —— `scripts/pipeline.mjs` 提到 `npm run pipeline`，步骤名用第七节那张表里的话。
3. **三个「站点」各归其名** —— 词条进 `GLOSSARY.md`，其余文档统一。
4. **同一段编排只留一份**（维护性，非理解性）—— 见 `docs/adr/0006-boundary-between-packages-and-scripts.md`。

## 六、明确不做

补建早期规划里的 `packages/resource-hub`（资源中台）、`n8n` 编排、Next.js 控制台。

理由：那三样是「多人协作 + 可视化编排」的解法，而这里是单人 + agent。补建会让代码量变成现在的数倍，并新增必须长期维护的运行组件（n8n 容器、前端构建）。这和「简洁简单」是反方向的。

原始规划见 `docs/网盘资源闲鱼自动化运营系统-设计方案.html`（L1–L5 五层 + n8n），本文件是它在 2026-10-15 的实际落地对照。
