## 一、现在的结构：五个常驻服务，一个镜像

全部由根目录的 `docker-compose.yml` 定义，共用一个镜像 `bdpan-goofish:local`。
**（2026-10-16 起这套东西跑在 `<SERVER_IP>` 上，路径 `/opt/bdpan-goofish`；下表的「127.0.0.1」指 134 的回环。）**

| 服务 | 容器名 | 端口 | 干什么 | 数据挂载 |
|---|---|---|---|---|
| `gateway` | `xgj-gateway` | 127.0.0.1:8787 | 闲管家「虚拟货源」回调网关 | `packages/xgj-gateway/data → /data` |
| `tunnel-xgj` | `xgj-tunnel-xgj` | — | 反向隧道：公网 `/goofish/*` → 本机网关 | 私钥只读挂载 |
| `tunnel-wechat` | `xgj-tunnel-wechat` | — | 反向隧道：公网 `/wechat*` → 本机微信服务 | 私钥只读挂载 |
| `wechat-serve` | `xgj-wechat` | 127.0.0.1:8899 | 公众号关键词自动回复 | `out`、`assets/free-software` 只读 |
| `admin` | `xgj-admin` | 127.0.0.1:8790 | 本机运营台 | 见下面「挂载清单」 |

**为什么隧道是两个容器而不是一个容器开两条 `-R`**：ssh 的 `ExitOnForwardFailure=yes`
会让任一端口冲突拖垮整条隧道。微信那条起不来事小，把闲管家回调链路（断了＝拍单不发货且无提示）
一起带断就是事故。所以两条隧道永远是两个进程 —— 现在只是从两个 launchd agent 变成两个容器。

**已经删掉的东西**：`cloudflared` Quick Tunnel（早被 SSH 隧道取代，长期没在跑）。

### 常用命令

```bash

docker compose up -d            # 构建并启动全部（幂等）
docker compose ps               # 状态
docker compose logs -f tunnel-xgj
```

## 二、首次切换（需要你亲手做）

> ⚠️ **本节已被第 0 节取代、未按此执行**：真实路径是「Mac 上的旧 launchd 隧道从未切到 Mac 的 Docker，
> 而是直接整体迁到了 134」。保留本节是因为它记录了「同一台机器上从 launchd 换成 compose」的做法，
> 将来若要在某台机器内部做这种替换，仍然适用（尤其是那个「必须一次做完、别让两条隧道并存」的约束）。

⚠️ **必须一次做完，中间不要停**：隧道用的是 `ExitOnForwardFailure=yes`，
launchd 的隧道和容器的隧道**不能同时存在**（远端 8787 端口只会被一个占住）。

```bash
cd /Users/noonebook/WorkBuddy/百度网盘mcp

# 1. 先只构建，验证镜像没问题（此时线上一切照旧）
docker compose build
docker compose config >/dev/null && echo "compose 配置合法"

# 2. 停掉旧的三个 launchd agent（隧道 + 微信服务）
launchctl bootout gui/$(id -u)/com.fmkj.xgj-tunnel    2>/dev/null
launchctl bootout gui/$(id -u)/com.fmkj.wechat-tunnel 2>/dev/null
launchctl bootout gui/$(id -u)/com.fmkj.wechat-serve 2>/dev/null

# 3. 停掉手跑的运营台（如果开着）
pkill -f 'xgj-admin/src/server.ts'

# 4. 起整套（这一步会重建 gateway 容器，约 2 秒中断 —— 挑没单的时候做）
docker compose up -d

# 5. ⭐ 验证：判据是**响应内容像不像我们自己的服务**，不是端口通不通
curl -s -o /dev/null -w '%{http_code}\n' https://xgj.fmkj.top/goofish/ping   # 期望 405
curl -s -o /dev/null -w '%{http_code}\n' https://xgj.fmkj.top/wechat        # 期望 403
open http://127.0.0.1:8790                                                  # 运营台应能打开

# 6. 注册新的开机自启（**必须在你自己的终端跑**，沙箱里注册不了 launchd）
bash scripts/install-agents.sh
bash scripts/install-agents.sh --status      # 应看到两条公网链路都是 ✔
```

### 回滚

旧的 plist 被改名保留为 `~/Library/LaunchAgents/com.fmkj.*.plist.disabled-20261015`：

```bash
docker compose down
for l in xgj-tunnel wechat-tunnel wechat-serve; do
  mv ~/Library/LaunchAgents/com.fmkj.$l.plist.disabled-20261015 \
     ~/Library/LaunchAgents/com.fmkj.$l.plist
  launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.fmkj.$l.plist
done
npm run admin        # 运营台回到手动跑
```

- 改代码后要 `docker compose build && docker compose up -d admin` 才生效（代码是烤进镜像的）。
- **图片体检改由 tesseract 做**，能力有缩水 —— 见下面第四节，这是唯一需要你决策的地方。

## 三、挂载清单（容器化最容易静默出事的地方）

判据不是「容器起来了」，而是「数据对不对」。切换后**务必打开运营台首页核对数字**
（商品数、卡密池、订单数应与切换前一致）。

| 服务 | 宿主路径 | 容器路径 | 权限 | 漏挂的后果 |
|---|---|---|---|---|
| gateway | `packages/xgj-gateway/data` | `/data` | rw | 卡密池空 → 拍单发不出货 |
| admin | `packages/xgj-gateway/data` | `/data` | rw | **页面照常渲染、数据全是 0**（实测 goods 从 758 变 0，无任何报错） |
| admin | `packages/xgj-admin/data` | 同路径 | rw | 店铺封控名单回退到镜像旧快照 → 封控期被静默绕过 |
| admin | `drafts` | `/app/drafts` | rw | 草稿列表空、发布失败 |
| admin | `out` | `/app/out` | rw | 体检结论丢失、发布护栏节流失效 |
| admin | `assets` | `/app/assets` | rw | 商品图渲染/上传失败 |
| admin | `.env` | `/app/.env` | ro | 扫描网盘/查线上商品缺凭据 |
| wechat-serve | `out` | `/app/out` | ro | 关键词表读不到 → 回复空 |

已经烤进镜像、**不需要**挂载的：`packages/`（各服务代码）、`scripts/`（含
`scripts/lib/preflight.mjs`，运营台运行时会动态 import 它）、`assets/_shared/`（违禁词表）。

> ⭐ 词表是**闸门的规则本身，不是数据**，所以跟代码一起烤进镜像 —— 少了它容器里的体检连规则都加载不了。

## 四、⚠️ 图片体检：tesseract 换得动，但**变弱了**（需要你决策）

### 背景

图片体检原本用 macOS Vision（`swiftc` 现编 `vision-scan.swift`）。Vision 只在 macOS 有，
Linux 容器里跑不了。所以新增了 `scripts/lib/ocr.mjs`：按平台自动选引擎。

| Vision 能力 | 判定后果 | Linux(tesseract) |
|---|---|---|
| ① OCR 读图里的字 → 查 GPT / CHATGPT 等 | **block，硬拦截** | ✅ 有 |
| ② 图像分类（~1300 类）→ bikini 等 | warn | ❌ **无替代，永久缺失** |
| ③ 肤色像素占比 | warn | ✅ 已用 JS 重写，实测与 Vision 差 <0.001 |

### 实测差异（`npm run ocr:diff` + `npm run ocr:diff:report`）

用 761 张历史商品图扫描结果做基准，**挑出 Vision 会判 block 的 3 张**（这才是唯一要紧的样本），
逐张跑 tesseract：

| 图 | Vision 拦的 | tesseract 拦的 | 结果 |
|---|---|---|---|
| `2cd271d7762d522b.png`（Blender GPT 插件） | `GPT` | `GPT` | ✅ 没漏 |
| `cee9e8c780db47d4.png`（AI Render 插件） | `STABLEDIFFUSION` | — | ❌ **漏判** |
| `cf1b26eb596895eb.png`（Blender Copilot） | `CHATGPT` `GPT` `OPENAI` | `CHATGPT` `GPT` | ❌ **漏判 OPENAI** |

原因不是分割模式，是**字体识别能力**：
- tesseract 把 "Stable Diffusion" 读成 `Wiffusion in B` / `Stala@e Liffusion`
- 把 "OpenAI" 读成 `Gopenar` / `Gopenal`

试过 `--psm 3/6/11/12`，也试过放大 2x/3x + 灰度 + 加对比度 —— **都没救**，
而且预处理会把中文段落打碎（"拍下后自动发..." 变成 `A Fe BMA BEM BBE`）。这条路排除。

**结论：tesseract 保住了「GPT / ChatGPT」这类最常见 token，但漏掉「Stable Diffusion /
OpenAI」这类拼写较长的。** 2026-10-08 那次封号正是 GPT 类，那条保住了。

### 现在的行为（已实现，不会静默）

- macOS 上一切照旧走 Vision，**行为与改动前完全一致**。
- 容器里走 tesseract，且**覆盖率会明确报出来**：
  - 命令行：`npm run preflight` 打印 `图片引擎 tesseract　①OCR读字 ✔　②图像分类 ✘　③肤色占比 ✔`
  - 运营台：体检结果的 `message` 里带 `⚠️ 当前图片引擎为 tesseract，图像分类不可用…`
- 缓存按引擎分目录（`out/.preflight/scan/<engine>/`），换引擎不会命中旧结果。

### 待你决策

三条路，见对话里的选项。**推荐**：Mac 上仍以 Vision 为准（发布前跑一次
`npm run preflight`），容器里的 tesseract 当作补充扫描；服务器上的图片体检问题推迟到
真的要搬机器时再定。

## 五、搬到别的机器（将来）

镜像不依赖 macOS（OCR 会自动切 tesseract），但下面几项**必须一起改**，否则会静默失效。

> ⚠️ **先分清目标是哪一种，第 1 条完全不同**：
>
> | 目标 | 要不起隧道 | 原因 |
> |---|---|---|
> | **公网服务器**（腾讯云那台自己跑） | ❌ 不要起隧道 | 网关就在公网机器上，闲管家直接打得进来 |
> | **内网机器**（如 `<SERVER_IP>`，Mac 的同类） | ✅ **必须保留隧道** | 内网 IP 公网到不了，只能由它反向连 `150.158.3.164` |
>
> 内网机的好处：**云服务器 Caddy 侧一个字都不用改**，只是隧道出口从 Mac 换成新机器。

### A. 内网机器（`<SERVER_IP>` 这类）

#### ⭐ 实测有效的完整配方（2026-10-16 就这么搬成的）

```bash
# ── 目标机准备：确认架构、Docker、磁盘 ──
ssh xgj134 'uname -m; docker --version; df -h /'

# ── 镜像：两端同架构时直接搬，不需要在目标机上 build ──
docker save bdpan-goofish:local | gzip -1 > out/.migrate/img.tar.gz   # 689MB → 171MB
scp out/.migrate/img.tar.gz xgj134:/root/
ssh xgj134 'gunzip -c /root/img.tar.gz | docker load'                 # ARM 上约 1~2 分钟

# ── 数据：约 32MB 的 tar.gz（代码 + 活数据内核 + .env + 私钥）──
#   打包见「数据卷搬迁」；注意 Linux 侧要清掉 macOS 带过去的 ._* 垃圾文件
ssh xgj134 'mkdir -p /opt/bdpan-goofish && tar -xzf /root/payload.tar.gz -C /opt/bdpan-goofish'
ssh xgj134 'find /opt/bdpan-goofish -name "._*" -delete'

# ── 把 .env 里两个 Mac 绝对路径改掉 ──
ssh xgj134 "cd /opt/bdpan-goofish && sed -i 's|^TUNNEL_SSH_KEY=.*|TUNNEL_SSH_KEY=/opt/bdpan-goofish/keys/workbuddykaifa.pem|' .env && \
            sed -i 's|^MEDIA_SSH_KEY=.*|MEDIA_SSH_KEY=/opt/bdpan-goofish/keys/workbuddykaifa.pem|' .env && \
            docker compose config >/dev/null && echo 配置合法"

# ── 起栈（隧道最后起，见下面第 2 条）──
ssh xgj134 'cd /opt/bdpan-goofish && docker compose up -d'
```

**踩过的四个坑**（每个都会静默出错）：

| 坑 | 现象 | 解法 |
|---|---|---|
| **Mac 的 launchd 隧道杀不掉** | 沙箱里 `launchctl` 完全不可用（`launchctl list` 返回 0 行），远端 8787 一直被旧隧道占着 | 把 plist 指向的 `~/bin/*.sh` **换成空转桩**（备份后替换，桩里 `exec sleep 86400` —— 直接 exit 会因 `KeepAlive=true` 打转重启） |
| **杀 node 主管进程不够** | node 被杀了，但它 spawn 的 **`ssh` 子进程成孤儿**，仍占着远端端口 → 服务器上表现为「端口在听但不转发」 | 必须**同时杀 `ssh` 子进程**：`lsof -nP -iTCP -sTCP:ESTABLISHED \| grep <服务器IP>:22` 找出 `ssh` 的 pid 再 `kill` |
| **macOS tar 带 `._*` 垃圾** | 目标机 `drafts/` 里出现 `._BD-XXX.json` 等 2313 个 AppleDouble 文件 —— 而「读 drafts 下所有草稿」的逻辑会把它们当草稿解析 | 解包后 `find <目标路径> -name '._*' -delete`；`tar` 的 `Ignoring unknown extended header keyword 'LIBARCHIVE.xattr.com.apple.provenance'` 警告本身无害 |
| **134 拉不到 Docker Hub** | 想 `docker compose build` → 拉不到 `node:22-slim` | 同架构就**不要 build，直接 `docker save`/`load`**（`registry-1.docker.io` 实测 000 超时，`registry.npmmirror.com` 正常，`deb.debian.org` 正常） |

**判成功**（不是「容器起来了」）：服务器侧 `curl --resolve xgj.fmkj.top:443:127.0.0.1 https://xgj.fmkj.top/goofish/ping` 期望 **405**、`/wechat` 期望 **403**；运营台 `/api/state` 的数字与迁移前**逐项一致**（本次实测 758/758/0、2 单、200 分、3 卡）。

> ⚠️ **下面的 1~6 条是 2026-10-15 的原始设想，已被上面的实测配方取代**（保留是为了记录「当初以为要做什么」）。
> 已知两处纠正：**134 上不需要 `install-agents.sh`/systemd**（靠 compose 的 `restart: unless-stopped`）；
> **运营台不要改成监听 `0.0.0.0`**（见第 3 条的反例，实况改用 SSH 端口转发）。

1. **起全部 5 个服务**（含两条隧道），隧道目标机换成新机器：
   ```bash
   docker compose up -d
   ```
   `.env` 里 `TUNNEL_SSH_HOST` 不变（还是腾讯云那台）。~~在这台新机器上跑 `scripts/install-agents.sh` 注册自启~~
   —— ❌ **实际没用这步**：五个容器全是 `restart: unless-stopped`，Docker 起来就自动回来。
2. ⭐ **云服务器、Caddy、DNS、图床全都不用动**。旧机器上的隧道要**先停**（远端 8787 只容得下一条隧道）。
3. ❌ **「把运营台改成 `0.0.0.0`」已否决**（2026-10-16 实况改用 SSH 端口转发）。
   原因：它**没有任何鉴权**却能直接上架到闲鱼（不可逆），暴露到局域网不可接受。
   → 正确做法：`admin` 保持只绑 `127.0.0.1:8790`，从 Mac 用
   `ssh -N -L 8790:127.0.0.1:8790 xgj134`（配套 plist `com.fmkj.admin-forward.plist`）。
   ⭐ 附带好处：`scripts/` 里 8 处硬编码 `127.0.0.1:8790` 一行都不用改。
   （真要局域网直连，再在目标机 `.env` 里加 `ADMIN_BIND=0.0.0.0`，自担风险。）
4. ⚠️ **架构必须对得上**：本机镜像是 `linux/arm64`（Mac 是 Apple Silicon）。
   先在新机器上 `uname -m`：
   - 同为 `aarch64` → 可以 `docker save | ssh 新机 docker load` 直接搬。
   - 是 `x86_64` → **镜像拷不过去**。两条路：① 在新机器上 `docker compose build`（推荐，734MB 基础镜像走内网很快）；
     ② 本机 `docker buildx build --platform linux/amd64 -t bdpan-goofish:local .`（走 QEMU，慢）。
5. ⚠️ **`XGJ_IP_WHITELIST` 保持 `false`**：经隧道进来时源 IP 是隧道出口，白名单没意义（与下面 B 相反）。
6. **数据**：见第四节 —— 内核只有 **≈6 MB**，`scp` 过去即可；大件按需。

### B. 公网服务器（网关就地跑）

1. **不要起隧道**。服务器上网关就在本机，不需要往回打：
   ```bash
   docker compose up -d gateway wechat-serve admin
   ```
2. **Caddy 改成直接反代本机端口**，不再经过 SSH 隧道：

   ```
   handle /goofish/* { reverse_proxy 127.0.0.1:8787 }
   handle /wechat*   { reverse_proxy 127.0.0.1:8899 }
   handle /goods/*   { root * /srv/goods-img; file_server }
   ```
   ⚠️ 必须用 `handle` 而不是 `handle_path`（后者会剥掉前缀，上游收不到正确路径）。
   改完 `systemctl restart caddy`（**不能 reload**）。
3. **`XGJ_IP_WHITELIST` 可以考虑打开**。现在是 `false`，因为经隧道进来时源 IP 是隧道出口。
   网关搬到服务器后就地收请求，源 IP 才是闲管家真实出口，白名单才有意义。
4. **图床跟着走**：`/srv/goods-img` 要么同机，要么把 `MEDIA_SSH_TARGET` 指向新位置。
   ⚠️ `xgj.fmkj.top` **同时是商品图床**，741 个草稿封面图 URL 都写着它 ——
   换域名必须连图床一起改（`drafts/*.json` 批量替换 + `.env` 的 `MEDIA_PUBLIC_BASE`）。

### 两种都一样要做的

5. **数据卷搬迁**：`drafts/`、`out/`、`assets/`、`packages/xgj-gateway/data/`、
   `packages/xgj-admin/data/` —— 这几个目录拷过去就行，都是 bind mount。
6. **DNS**（仅当公网 IP 变了）：`xgj.fmkj.top` 必须解析到新服务器。⚠️ 公网返 `404` + `server: Caddy`
   ＝打到了**别的** Caddy（先查 DNS，别动隧道）。
7. **OCR**：服务器上没有 Vision，只能 tesseract —— 见第四节。
8. ⚠️ **`drafts/` 与网关 `data/` 是「活数据」，同一时刻只能有一台机器在写。**
   切换顺序必须是「**先停旧机器（含 launchd 自愈与手跑的运营台），再起新机器**」，
   否则两边并发写 `.listings.json` / `cards.json` 会把台账写坏。
