# 主线走「虚拟货源」应用，而非「进销存」

闲管家提供两套开放平台应用，数据流方向相反：进销存是我们把数据推给管家，虚拟货源是管家回调我们。主线选了虚拟货源，因为它有**原生发货**——买家拍单后管家直接调我们的接口取卡密，我们不必自己实现发货逻辑。

代价是必须自建公网入口（自有服务器 + SSH 反向隧道回到本机），并长期承担隧道运维。进销存那套的 API 上架能力保留在 `goofish-adapter` 里，但不在主线上使用。

## Considered options

- **进销存**：有 API 创建商品的接口，虚拟货源没有；但发货要自己写。
- **虚拟货源**：发货原生，但需要自建公网网关。

发货闭环比「能上架」更难自建，所以接受了自建网关的运维成本。

## Consequences

两套应用的签名算法与凭证不通用，写代码前必须先确认应用类型（`GOOFISH_ERP_APP_*` 是进销存，`GOOFISH_APP_*` 是虚拟货源）。

隧道断掉时平台不会报错，只是不发货——运维上必须主动探测，判据见 `.workbuddy/memory/MEMORY.md` 的隧道自愈条目。
