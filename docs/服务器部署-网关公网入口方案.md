# 公网入口方案：从 Quick Tunnel 到固定地址

> 2026-10-08 · 起因：当天 Quick Tunnel 被回收，导致买家拍单没发货（详见文末事故记录）

---

## 一、先说清楚一件事：为什么"没开发完"不是不动的理由，但确实有一个真理由

**伪理由（不成立）**：以为要等开发完成才能动。其实不成立 ——
需要公网可达的只有**网关容器**，它是自包含的：

| 网关依赖什么 | 实测 |
|---|---|
| 环境变量 | 只有 7 个：`XGJ_DATA_DIR` / `XGJ_PORT` / `XGJ_MCH_ID` / `XGJ_MCH_SECRET` / `GOOFISH_APP_KEY` / `GOOFISH_APP_SECRET` / `XGJ_TIMESTAMP_TOLERANCE` |
| 状态 | 只有 4 个 JSON：`cards.json` / `catalog.json` / `orders.json` / `subscriptions.json` |
| 是否碰百度网盘 | **完全不碰**（百度凭证不注入这个容器） |
| 管理端（出图、发布） | 依赖本机 Chrome + ssh/scp 私钥，**本来就不该进容器** |

**真理由（成立）**：**`card-sync` / `ops-check` / `check-delivery` 这三个脚本是直接读写 `packages/xgj-gateway/data/*.json` 的。**
网关一旦搬走，这三个脚本的写入目标必须一起改成"写远程"，否则会出现
**「本机改了卡密池，服务器上的网关看到的还是旧的」**——这是很隐蔽的数据分叉。

所以：**「完整迁移」确实适合等开发告一段落再做**；但**「把公网入口固定下来」不必等**，两者可以分开。

## 二、三个选项

| | 方案 A · SSH 反向隧道 + 服务器 Caddy | 方案 B · 完整迁移 | 方案 C · 保持现状 |
|---|---|---|---|
| 公网地址 | **固定** `https://xgj.fmkj.top` | **固定** 同上 | 每次重启都变 |
| 网关跑在哪 | 仍在本机 | 服务器 | 本机 |
| 要改本机代码 | **不用** | 要（card-sync 等 3 个脚本） | 不用 |
| 服务器要装什么 | **什么都不用**（sshd 已有） | Docker + 构建镜像（x86 需重新构建*） | 不用 |
| 工作量 | 小（约 20 分钟） | 中大（半天以上） | 0 |
| 依赖 | 本机常开 + ssh 连接保活 | 服务器常开 | 本机常开 + Cloudflare |
| 遗留风险 | ssh 断线需保活 | 无 | **隧道会被回收（已发生）** |

\* 本机是 `arm64`、服务器是 `x86_64`，本地构建的镜像（`arm64/linux`）**不能直接在服务器跑**，必须在服务器上重新构建。

## 三、推荐：方案 A（已验证可行）

### 原理

```
闲管家 ──HTTPS──> xgj.fmkj.top (Caddy, 150.158.3.164)
                        │  handle /goofish/*  → 反向代理
                        ▼
                 127.0.0.1:8787 (服务器本地端口)
                        ▲
                        │  SSH 反向隧道（本机主动连出去，无需公网 IP）
                        │
            本机 Mac：xgj-gateway 容器 127.0.0.1:8787
```

地址是 `xgj.fmkj.top`——**你已经在用的图床域名**，指向同一台服务器。
所以**不需要新域名、不用碰 DNS、不用动证书**，只是在 Caddyfile 里加一段路径路由。

### 已验证

临时用 18787 端口实测过这条链路：
```
$ ssh -N -R 127.0.0.1:18787:127.0.0.1:8787 root@150.158.3.164
$ # 然后在服务器上：
$ curl http://127.0.0.1:18787/__health
{"ok":true,"service":"xgj-virtual-source-gateway","time":"2026-10-08T05:53:34.819Z"}
$ curl -X POST http://127.0.0.1:18787/goofish/open/info -d '{}'
{"code":1000,"msg":"商户不存在：(空)"}
```
→ 服务器确实能打到本机网关。测试隧道已关闭，未影响任何现有服务。

### 需要做的三步

**1. 服务器 Caddyfile 加一段路由**（⚠️ 现有配置是图床，改动前先备份 + `caddy validate`）

```caddyfile
xgj.fmkj.top {
	# 新增：闲管家回调走这里。注意用 handle（不剥前缀），
	# 不能用 handle_path —— 它会把 /goofish 也剥掉，上游就收不到正确路径了
	handle /goofish/* {
		reverse_proxy 127.0.0.1:8787
	}

	# 以下为原有图床配置，保持不变
	handle_path /goods/* {
		root * /srv/goods-img
		file_server
		header Cache-Control "public, max-age=31536000"
	}
	handle {
		respond "media host" 200
	}
}
```

**2. 本机跑一条带保活的 SSH 反向隧道**

```bash
ssh -N -R 127.0.0.1:8787:127.0.0.1:8787 \
    -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -o ExitOnForwardFailure=yes \
    -i ~/Downloads/workbuddykaifa.pem root@150.158.3.164
```
（断线自动重连建议包一层 autossh 或 launchd，我可以做成 `npm run tunnel:ssh` 一键脚本）

**3. 闲管家「我的应用 → 货源授权信息 → 接口网关」填**

```
https://xgj.fmkj.top
```
（填域名部分，结尾不带 `/goofish`）

### 方案 A 的说明

- **真实客户端 IP 是能拿到的** —— 我一开始判断错了，以为 SSH 隧道会让 Caddy 只看到 `127.0.0.1`。
  实际上 `X-Forwarded-For` 是**在 HTTP 层传递的，不受 TCP 转发影响**：
  Caddy 收到真实客户端连接后自己设置 XFF，网关再读 XFF。实测验证：

  ```
  本机公网 IP        : 175.8.39.114
  网关日志看到的来源 : 175.8.39.114        ← 一致，说明 XFF 透传成功
  Caddy 未配置 trusted_proxies（默认不信任客户端自带的 XFF，自己设置 → 可信）
  ```

  → 所以 **`XGJ_IP_WHITELIST=true` 是可用的**，不必等方案 B。
  （但见下方"要不要现在开"的权衡）
- **依赖本机在线**：跟现在一样（现在也依赖本机跑 cloudflared + gateway）。
- 旧隧道可以留着当备份，只是闲管家只能填一个地址。

## 五、方案 C：什么都不动

靠 `npm run watch:tunnel` 的**每小时巡检**兜底（已建自动化）：
- 隧道不可用 → 通知你
- 地址发生变化 → 通知你「必须去闲管家重填」

代价：地址变化时仍需人工去闲管家改一次（闲管家没有改接口网关的 API，这步无法自动化）。

## ⚠️ 两件需要你手动做的事

**1. 闲管家「接口网关」改成固定地址**（这一步只能人工）

```
https://xgj.fmkj.top
```
路径：闲管家 → 我的应用 → 货源授权信息 → 接口网关（填域名部分，结尾不带 `/goofish`）

**2. 让隧道开机自启**（本会话的沙箱不允许注册 launchd 服务，实测
`Bootstrap failed: 5: Input/output error`，连最简 plist 都失败 —— 所以这一步得你在自己的终端跑一次）

plist 和包装脚本**我已经建好了**（`~/Library/LaunchAgents/com.fmkj.xgj-tunnel.plist` + `~/bin/xgj-tunnel.sh`），你只需要执行：

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.fmkj.xgj-tunnel.plist
```

之后开机自启、断线自愈。管理命令：
```bash
launchctl list | grep fmkj                                                    # 看状态
launchctl bootout gui/$(id -u)/com.fmkj.xgj-tunnel                            # 停用
tail -f ~/Library/Logs/xgj-tunnel.log                                         # 看日志
```

**在你执行之前**，链路靠两条保障：① 每小时巡检发现断了会自动重启隧道；② 巡检正常时保持安静。

> ⚠️ 一个已知限制：`nohup ... &` 起的隧道进程**会随 shell 退出被回收**（实测过）。
> 巡检自愈用的是 Node 的 `detached` 方式，比 nohup 抗得住；但真正可靠的还是 launchd。

## 要不要开 IP 白名单？

现在技术上**可以**开（`XGJ_IP_WHITELIST=true`），但建议**先不开**：

- ✅ 好处：多一层纵深防御，挡掉一切非闲管家的流量
- ⚠️ 风险：闲管家官方 IP 段（`112.74 / 120.24 / 120.78 / 120.79 / 39.108 / 47.106 / 120.77` 各 /16）
  是他们单方面给的，**如果他们调整了出口 IP，订单会静默失败**，排查成本很高
- 当前已有**签名校验**（appId + appSecret + mchId + mchSecret + 时间戳）在认证来源，
  白名单属于"锦上添花"而非"必需品"

建议：等链路跑顺、确认稳定出单一段时间后再开，并在此期间留意有没有非官方 IP 的请求。
