二、本轮最有价值的发现：阶段一根本不需要分享接口

把「分享」从自动化链路里摘出去，剩下的全部可做

之前的方案里，我默认「自动发货 = 下单后实时调 AI 生成分享链接」，于是百度那个付费分享接口变成了 P0 阻塞。这个前提可以改。

「创建分享链接」这个动作，人在网盘客户端点一下只要几十秒，而且没有任何次数限制、没有认证门槛、完全免费。接口只是把它自动化而已。
所以阶段一改成：你手动建一批分享链接 → 灌进闲管家卡密池 → 闲管家原生自动发货。百度 API 一次都不用调。

阶段一的真实代价，得说清楚

预置链接是共享的——所有买家用同一个链接。买家拿到后转手卖给别人，你无法从技术上阻断。应对办法是组合使用：① 用百度网盘的「分享有效期」设为 7 天或 30 天，压住长期扩散；② 定期轮换链接；③ 商品描述里写清"仅供个人使用"。等到阶段二上线，再逐步切到一单一链。

三、签名验证：证据与边界

签名是整条链路的钥匙。两件事分开验证，我把证据和证据不够的地方都摆出来。

3.1 算法正确性 —— 对官方测试向量（离线，确凿）

官方《接入说明》给了一组测试向量，npm run verify:sign 可以直接复现：

输入：
  appKey    = 203413189371893
  appSecret = o9wl81dncmvby3ijpq7eur456zhgtaxs
  timestamp = 1636087298
  body      = {"product_id":"219530767978565"}

实测输出：
  bodyMd5 = 2608f2139cca8755cabf25209251e549   ← 与官方期望一致 ✅
  sign    = c26c8a48809141f3dd80bd9b9ddb41ea   ← 与官方期望一致 ✅

这条证据是确凿的：md5 中间值和最终签名都对得上，说明拼接格式（appKey,bodyMd5,timestamp,appSecret）、压缩 JSON 的处理、字符编码全都正确。

3.2 请求格式被服务端接受 —— 真实请求

我用官方文档里公开的示例凭证，向生产网关发了真实请求：

POST https://open.goofish.pro/api/open/user/authorize/list?appid=…×tamp=…&sign=…
Content-Type: application/json; charset=utf-8
body: {}

服务端应答：
{"code":100001,"msg":"203413189371893:应用不存在或已下线","data":{}}

对照组（故意写错路径）：
POST https://open.goofish.pro/api/open/__definitely_not_real__
→ HTTP 404  404 page not found

对照很关键：路径对 → 返回 JSON 业务错误；路径错 → 返回 404 纯文本。所以能确认：接口路径正确、appid 参数被正确读取、POST + JSON 请求体被接受。

⚠️ 我原本要下的一个错误结论，被对照实验推翻了

看到 code=100001（而不是 401 签名错误）时，我一度以为「签名被服务端接受了」。于是补做了对照实验：完全不带 sign、sign 传垃圾值——结果返回的是一模一样的 100001。

这说明服务端的校验顺序是「先查 AppID，再验签名」。应用不存在时服务端拿不到 appSecret，根本无从验签。
所以这条证据只能证明请求格式与路径正确，不能证明签名被接受。签名的可靠性目前由 §3.1 的官方向量自检保证；真实的线上验签，要等填上你的 appKey 才能确认——这也是 gf:ping 的设计意图：凭证一到手，第一件事就是验它。

五、打通全链路：你需要做的三步

前置条件（一次性，约 1 个工作日）

闲管家的接入条件比较硬：注册闲管家账号 → 绑定闲鱼店铺 → 店铺具备鱼小铺资质 → 订购开放平台版本（ERP 专业版或铂金版）→ 在「我的应用」创建进销存类型应用 → 填 IP 白名单 → 应用上线。
注意两点：① 高级版不能创建应用，必须专业版或铂金版；② 应用类型必须是「进销存」，否则接口一律报「应用不存在或已下线」。

1
把凭证给我 在闲管家「我的应用」页复制 AppKey 与 AppSecret。另外告诉我你的闲鱼会员名（上架目标店铺），以及当前出口公网 IP——本机若挂着代理，出口 IP 是代理服务器的，不是宽带的，这个坑我在地图上标了。
2
我跑探针，把三件事一次验完 npm run gf:ping 会依次确认签名是否被接受、IP 是否在白名单、应用是否上线。失败会给出对应的排查清单（401 查什么、403 查什么、100001 查什么）。
3
查类目 → 回填 → 上架 gf:categories 拿到类目 ID 与必填属性，填进 drafts/00-联调测试.json，然后 gf:publish --live。这条测试商品价格故意定成 999 元、库存 1 件，验证完立即删除。

5.1 联调测试商品长什么样

这是为了「跑通线路」专门做的，不涉及任何版权问题：

标题：  【接口联调专用】请勿购买 自动化链路测试商品
价格：  ¥999.00（单位是「分」，写 99900）  库存：1

描述：  说明这是链路验证商品，验证完成后删除

{"item_biz_type":2,"sp_biz_type":99,"channel_cat_id":"<类目ID>","channel_pv":[],
 "price":99900,"express_fee":0,"stock":1,"stuff_status":100,"outer_id":"TEST-CONN-001",

它还带了一份 drafts/10-Procreate室内设计笔刷.json，是从你网盘里的真实资源生成的可上架范例——商品文案直接从目录结构反推卖点。但它的 compliance.clean 我设成了 false，因为那个目录里有他人淘宝店的书签、版权来源不明。这样它会被硬闸门挡住，正好演示闸门怎么起作用。

七、发货链路的两种设计

7.1 阶段一：闲管家原生发卡（零代码）

1. 你在网盘手动创建分享链接（有效期建议 30 天）
2. 把 "链接 提取码" 作为一条卡密，灌进卡种库存：
   POST /api/open/kami/storage/create
   { "kind_id": <卡种ID>, "cards": ["链接:https://pan.baidu.com/s/xxx 提取码:abcd"], "is_repeat": false }
3. 在闲管家后台把「发卡组合」绑定到商品，开启虚拟自动发货
4. 买家下单 → 闲管家自动发一条卡密给他 → 完成

需要你在后台确认一件事

「发卡组合怎么绑定到具体商品」这一步，官方文档里只有 group/create（字段是 group_name + kind_group）和 group/update/status，没有出现商品 ID 字段。推测绑定入口在闲管家后台的商品编辑页（虚拟发货设置）。这一步拿到账号后我看一眼就能确认，先不猜。

7.2 阶段二：一单一链（拿到分享权限后）

买家下单
  ↓ 闲管家推送（超时 3 秒，官方建议先返回 success 再异步处理）
POST 你的回调地址  ?appid=…×tamp=…&sign=…
body: { "order_no": "...", "order_type": 7, "order_status": 2, ... }
  ↓ 验签（推送的签名不含 seller_id）
md5("应用KEY,Body报文Md5值,时间戳,应用密钥")
  ↓ 生成该订单专属的网盘分享链接（调百度分享接口）
  ↓ 发货
POST /api/open/trade/logistics/dummy/send
{ "order_no": "...", "send_way": 2 }
  ↓ 记台账：订单号 ↔ 分享链接 ↔ 有效期
退款推送到达 → 精确作废该订单的链接

这一段代码已经写好了：push.ts 里有验签、时间戳容差（官方 5 分钟，我放宽到 10 分钟抗时钟漂移）、以及把推送报文翻译成「该不该发货」的判定逻辑。

关于 service_support 这个字段

官方 FAQ 第 12 条明确：「service_support 商品服务不是传参就能用的，闲鱼 APP 要开通相关服务才能使用」。传了但店铺没开通，上架会直接报「未开通服务或当前品类不支持开通服务; [2]-[99]」。所以我在草稿校验里加了警告——默认别填。
