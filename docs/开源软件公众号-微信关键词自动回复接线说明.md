# 开源软件公众号 · 微信「关键词自动回复」接线说明

> 2026-10-09 · 对应实现：`scripts/wechat-reply-server.mjs` + `scripts/lib/wechat-reply.mjs`
> 本地自测：`npm run wechat:selftest`（当前 **14/14 通过**，不需要公网、不需要扫码）

---

## 一、先说最省事的一点：**你不需要 AppSecret**

| 能力 | 需要什么 | 说明 |
|---|---|---|
| **关键词自动回复**（用户发消息 → 我们回一条） | **只要 Token** | 走「消息接口」，微信只校验 Token 签名。Token 是**你自己定的一串字符**，不是微信发给你的 |
| 主动推送 / 群发 / 管理素材 / 获取用户信息 | 需要 AppSecret | 本服务**刻意不读取 AppSecret**，配置泄露也只泄露自己定的那个字符串 |

所以测试号页面上那两栏：

- **URL** ← 填我们的公网地址（见第三节）
- **Token** ← 你自己定一个（例如 `workbuddy-oss-2026`），只要和服务端启动参数一致即可

AppSecret **不用填进任何地方**，暂时不需要它。

> ⚠️ 安全提醒：AppSecret 已经出现在聊天记录里了。测试号的密钥风险不高，但这个习惯要改过来 —— 真正需要用 AppSecret 的那天（比如做主动推送），把它放进**本地 gitignore 的 env 文件**，不要写在文档或代码里。

## 二、本地先验证（不碰公网）

```bash
npm run wechat:selftest          # 离线跑 14 项断言：签名、XML、关键词、异常字符、事件消息
```

自测覆盖的东西（这些如果等到线上才发现会很烦）：

| 覆盖点 | 为什么重要 |
|---|---|
| GET 签名正确 → 原样返回 `echostr` | 测试号点「提交」就是打这个，失败会一直提示"配置失败" |
| GET 签名错误 → 403 | 防止填错 Token 时静默通过 |
| 大小写 / 前后空格归一化 | 手机上打字常带空格 |
| 「只介绍」类不给网盘链接 | 合规红线，不能靠人记 |
| 未命中 → 提示 + 帮助 | 不能对着用户沉默 |
| 包含式兜底（"我要 Maccy 的链接"） | 只在**唯一命中**时采用，避免误回 |
| `]]>`、`<`、`&` 等异常字符 | CDATA 里出现 `]]>` 会把 XML 撑坏，微信直接报错 |
| 图片 / 语音等非文本消息 | 回帮助而不是 500 |
| 关注事件 | 关注时自动推目录，转化关键位 |

起服务：

```bash
WECHAT_TOKEN='你定的token' npm run wechat:serve
# → 监听 127.0.0.1:8899，路由 /wechat
curl http://127.0.0.1:8899/health    # 看读到了多少关键词、链接配了几条
```

## 三、暴露到公网（**已配置并验证通过**）

微信要求 URL 是公网可访问，且**只支持 80 / 443**。复用了现有公网入口，没新建域名：

```
微信服务器 → https://xgj.fmkj.top/wechat
                  └ Caddy: handle /wechat* → 127.0.0.1:8899（服务器本地）
                                              ▲
                                              │ 本机**另一条独立**的 SSH 反向隧道
                                              │
                                本机 Mac: wechat-reply-server 127.0.0.1:8899
```

`/etc/caddy/Caddyfile` 里实际加的内容（已生效）：

```caddyfile
	# ── 微信公众号「关键词自动回复」──
	handle /wechat* {
		reverse_proxy 127.0.0.1:8899
	}
```

⚠️ **三个关键点**（来自这段时间的运维经验）：

1. **用 `handle /wechat*` 而不是 `/wechat/*`** —— 后者要求带尾斜杠，而测试号里填的是 `https://xgj.fmkj.top/wechat`（无尾斜杠），会漏到兜底路由去。
2. **改完必须 `systemctl restart caddy`，不能 `reload`** —— reload 在这台机器上不生效。改前已备份 `/etc/caddy/Caddyfile.bak-20261009-084910`（回滚＝覆盖回去 + restart）。
3. **8787 那条闲管家链路一个字都没碰。** 微信侧是**另起一条独立隧道**（`TUNNEL_NAME=wechat`，8899），而不是往 8787 那条上加一个 `-R`。原因：多转发时 `ExitOnForwardFailure=yes` 会让**任一端口冲突拖垮整条隧道** —— 微信侧起不来事小，把闲管家回调链路带断就是事故。

### 验证结果（2026-10-09 08:49）

| 检查项 | 结果 |
|---|---|
| `caddy validate` | `Valid configuration` |
| `GET /wechat?…&echostr=x` | 原样返回 `x`，HTTP 200 |
| `POST /wechat`（内容 `Maccy`） | 返回回复 XML（含仓库地址 + 链接占位） |
| `GET /`（原有兜底） | 200 |

| `GET /goods/*`（图床） | 404（文件不存在，正常） |

## 三·补、让它在重启后自动恢复（**需要你在自己的终端跑一次**）

当前两个进程是**临时起的**，电脑重启或会话结束就没了。要常驻得用 launchd：

```bash
cd "/Users/noonebook/WorkBuddy/百度网盘mcp"
npm run wechat:agent               # 安装并启动（开机自启 + 断线自愈）
npm run wechat:agent -- --status   # 只看状态
npm run wechat:agent -- --remove   # 卸下
```

⚠️ **必须在你自己的系统终端里跑**：本项目的沙箱环境不允许注册 launchd
（实测 `Bootstrap failed: 5: Input/output error`，连最简 plist 都失败）——
和当初配 8787 隧道时是同一个限制。

它做的事（`scripts/install-agents.sh`）：把 `~/Library/LaunchAgents/com.fmkj.*.plist` **全部**交给 launchd 托管 —— **包括闲管家 8787 那条**。三个 agent 都配了 `RunAtLoad + KeepAlive`，开机自启、进程崩了自动拉起。

| plist | 包装脚本 | 管什么 |
|---|---|---|
| `~/Library/LaunchAgents/com.fmkj.wechat-serve.plist` | `~/bin/fmkj-wechat-serve.sh` | 关键词回复服务（8899） |
| `~/Library/LaunchAgents/com.fmkj.wechat-tunnel.plist` | `~/bin/fmkj-wechat-tunnel.sh` | 8899 反向隧道 |

日志：`~/Library/Logs/fmkj-wechat-serve.log` / `fmkj-wechat-tunnel.log`

> 💡 **顺带发现一个问题**：闲管家那条 8787 的托管 `com.fmkj.xgj-tunnel`
> **当前也没有被 launchd 加载**（`launchctl list` 里查不到 fmkj 条目），
> 现在它靠一个游离进程在跑。**电脑一重启，闲管家回调链路就会断**
> （断＝拍单不发货且无提示）。建议一起补上：
> ```bash
> launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.fmkj.xgj-tunnel.plist
> ```

## 五、网盘链接怎么填

链接**不写在代码里**，放在 `assets/free-software/netdisk-links.json`：

```json
{
  "maccy": "https://pan.baidu.com/s/xxxxx 提取码 abcd"
}
```

- 键 = 项目 id（和 `out/keywords-table.json` 的 id 一致）
- **没填的项目会显示 `[网盘链接占位]`** —— 这是故意的，避免误发空链接
- 改完**不用重启**，服务按文件修改时间自动热加载
- 铁规不变：**网盘链接只在自动回复里给，不进文章正文**

## 六、常见坑（都是会在线上浪费半天的）

| 现象 | 真因 |
|---|---|
| 点「提交」一直提示配置失败 | 服务没起 / 公网没通 / **Token 与本地不一致**（最常见） |
| 配置成功但发消息没反应 | 服务端在 5 秒内没返回。本服务是本地读文件，不会超时；若代理层有缓冲，检查反代是否等待响应体 |
| 回复内容被截断 | 微信被动回复文本上限 **2048 字节**，服务已按 UTF-8 截到 2000 并加省略号 |
| 回复里出现奇怪字符或微信报错 | CDATA 里的 `]]>` 没断开。`buildTextReply()` 已处理 |
| 本地测通、线上不通 | 十有八九是 Caddy 的 `handle` 优先级或路径没匹配上（注意结尾 `/*`） |
| 改了链接不生效 | 检查是不是改到了别的文件；服务只认 `assets/free-software/netdisk-links.json` |

## 七、和「定期跟版本」的联动（后续）

`out/keywords-table.json` 里的 `version` 字段来自 `gh-audit`。所以：

```bash
npm run gh:watch        # 看哪些项目出了新版
npm run gh:audit        # 刷新台账（版本号跟着更新）
node scripts/gen-keywords.mjs   # 关键词表重新生成 → 回复里的版本号自动变新
```

**不用手改回复文案**。这就是台账驱动的意义。
